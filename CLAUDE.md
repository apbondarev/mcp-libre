# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
uv sync                              # install dependencies

./quick-test.sh test                 # built-in functionality tests (= python src/main.py --test)
./quick-test.sh server               # start the stdio MCP server
./quick-test.sh client               # interactive in-process MCP client (tests/test_client.py)
./mcp-helper.sh check                # verify LibreOffice/Python/uv prerequisites
./mcp-helper.sh demo                 # interactive demo (examples/)
./generate-config.sh claude          # write ~/.config/claude/claude_desktop_config.json with real paths

uv run pytest tests/ -v              # 28 tests
uv run pytest tests/test_cursor_info.py                   # no LibreOffice needed
uv run pytest tests/test_insert_fix.py::test_edge_cases   # single test
```

Two kinds of test live here. `test_cursor_info.py` and `test_document_type_dispatch.py` are real asserting tests that run in the venv, because `tests/uno_stubs.py` fakes the `uno` and `com.sun.star.*` modules so `plugin/pythonpath/` becomes importable — see the caveat in `tests/fake_writer.py` about what fakes cannot prove. `test_client.py` and `test_insert_fix.py` are older print-driven scripts that shell out to real LibreOffice and return booleans instead of asserting, so their green runs prove little — read their output. `test_client.py::test_mcp_client` fails on collection because `pytest-asyncio` is not enabled (no `asyncio_mode` in `pyproject.toml`); that predates any current work.

No linter or formatter is configured; `ruff` is not a dependency despite what `QWEN.md` says.

## Architecture

Two **independent** MCP server implementations live here. They share no code; a change in one is not a change in the other.

### 1. External server — `src/libremcp.py` (14 tools, stdio)

A single-file FastMCP server that manipulates documents **as files on disk**, driving LibreOffice through `subprocess` (`libreoffice --headless --convert-to ...`). It never talks to a running LibreOffice instance, so it has no concept of the active document, the cursor, or the selection.

Consequences worth knowing before adding a tool:

- `_run_libreoffice_command` tries `libreoffice`, `loffice`, `soffice` in order.
- Text extraction (`read_document_text`) converts to `.txt` in a temp dir, then falls back to unzipping `content.xml` (`_extract_text_from_odt`), then to reading raw bytes.
- **Editing is destructive by design.** `insert_text_at_position` reads all text, concatenates, and *recreates* the file (`_recreate_writer_document` → LibreOffice conversion → `_create_minimal_odt` hand-written ODT zip). All formatting, styles, and images are lost. A `.backup` copy is restored on failure. `_insert_text_writer_document` is dead code — it builds a UNO macro string and then `return False` unconditionally.
- Resources: `documents://` (rglob over `~/Documents`, `~/Desktop`, cwd) and `document://{path}`.
- `main()` handles `--test`, `--help`, `--version` before `mcp.run()`; startup chatter goes to stderr so stdio JSON-RPC stays clean.

Entry points: `src/main.py` does a flat `import libremcp`, which works only because Python puts the script's own directory on `sys.path` — hence `PYTHONPATH=<repo>/src` in the config templates. The root `libremcp.py` is a 6-line vestigial stub, not the server; `pyproject.toml`'s `[project.scripts]`/hatch `packages` still point at stale paths.

### 2. Embedded plugin — `plugin/pythonpath/` (22 tools, SSE over HTTP :8765)

Runs *inside* LibreOffice via UNO, so it acts on live open documents with no file I/O. Four layers:

- `registration.py` — the UNO component. Registered as a `com.sun.star.frame.ProtocolHandler` (see `ProtocolHandler.xcu`) for the `org.mcp.libreoffice.extension:` protocol; `Addons.xcu` menu items dispatch URLs like `...:start_mcp_server` into `MCPExtension._execute_action`. Server state lives in module-level globals shared across instances; start/stop run on daemon threads.
- `ai_interface.py` — MCP SSE transport on a `BaseHTTPRequestHandler`: `GET /sse` opens a stream and mints a session, `POST /messages?sessionId=` accepts JSON-RPC whose replies are pushed back over that session's queue. Also `GET /health`, `/`, `/tools` for debugging. Implements `initialize`, `tools/list`, `tools/call`, `ping` by hand (protocol version `2024-11-05`).
- `mcp_server.py` — `LibreOfficeMCPServer` (lazy singleton via `get_mcp_server()`), a `self.tools` dict of `{description, parameters (JSON Schema), handler}` plus thin `*_live` handlers.
- `uno_bridge.py` — the only place that touches UNO objects (`Desktop`, `XTextDocument`, `XSpreadsheetDocument`, `PropertyValue`).

**Adding a plugin tool means three edits**: a `UNOBridge` method, a `*_live` handler, and a `self.tools[...]` entry in `_register_tools` (the JSON Schema there is what clients see — `execute_tool` splats it as `**parameters`).

Hard constraints on plugin code:

- **No external programs. A tool must work with nothing but LibreOffice and the Python standard library, on any machine where LibreOffice runs.** No `pdftoppm`, no ImageMagick, no `gs`, no screenshot utility — a capability that needs one of those is not a capability of this server. Whatever is wanted is either reachable through UNO (a filter, `XRenderable`, `GraphicProvider`) or it is not offered at all. This is a requirement on every tool, not a preference: the server is installed as a LibreOffice extension on machines whose contents nobody controls.
- It runs under LibreOffice's bundled Python: **stdlib only**. No `pip` deps, no `mcp`, no `httpx`, no `pydantic`. That's why the SSE transport and JSON-RPC are hand-rolled.
- Errors are returned as `{"success": False, "error": ...}` dicts rather than raised, since exceptions inside UNO callbacks vanish.
- **Never do UNO work on a thread of your own while the main thread shows a modal dialog.** A dialog runs a nested event loop holding the SolarMutex; a Python thread cannot acquire it, and the process dies with no traceback — `/tmp/mcp_extension.log` simply stops. This crashed LibreOffice on "Start MCP Server" until `_execute_action` was made synchronous. UNO from an HTTP handler thread is fine while the main thread sits in its normal event loop, which is why tool calls work.
- `AIInterface.stop()` signals open SSE sessions *before* `shutdown()`/`server_close()`, and `MCPHTTPServer` sets `daemon_threads = True`. Without both, one open stream blocks shutdown forever, because `server_close()` joins non-daemon handler threads.
- `MCP_EXTENSION_LOG` overrides the log path, which is how tests avoid appending to the file you are tailing.
- `plugin/description.xml` `identifier`/`version` must stay in sync with the hardcoded `org.mcp.libreoffice.extension` in `install.sh` and `build.sh`'s `VERSION`; `META-INF/manifest.xml` lists exactly which files LibreOffice loads.
- **`isinstance` never works on UNO objects.** Every proxy is `<class 'pyuno'>` and inherits none of the imported `com.sun.star.*` interfaces, so `isinstance(doc, XTextDocument)` is always False — silently, since the fallback branch just reports "unknown". Use the `_supports(obj, service)` helper in `uno_bridge.py` with a service name instead. This defect had disabled `get_text_content`, `insert_text`, `format_text` and every document-type report until it was fixed.
- A text range belongs to the text that owns it. Inside a table cell or a frame that is *not* `doc.getText()`, and passing a foreign range to the body text throws "End of content node doesn't have the proper start node" — so build cursors from `range.getText()`, as `get_cursor_info` does.
- `insertString(cursor, text, bAbsorb)` — the last flag decides insert vs replace. `insert_text` passes `False`, so with a selection it inserts at the selection start and leaves the original: that is why "translate and replace" produced both texts. `replace_selection` rewrites the resolved range with `setString` instead.
- Every mutation goes through `_guarded_edit(doc, undo_title, track_changes, edit)`: read-only refusal, one undo context, the three-state recording contract, and the document's own setting restored. Add a mutating tool by writing the `edit` closure, not by repeating the guards.
- `replace_range`/`replace_selection` **refuse** a range holding more than one run, or any hyperlink, unless `flatten=true`: replacing such a range with one string destroys inline code, italics and links, and the tool can see that before writing. `read_runs` + `replace_runs` is the route that keeps them. A character style on a *single* run survives a flat replacement, so that alone is not a refusal — measured, along with the fact that a link does not survive even as the only run.
- A pyuno enum stringifies as `<Enum instance com.sun.star.awt.FontSlant ('ITALIC')>`, so read its `.value`. Testing `str(...)` reported every run as upright, and the fakes hid it by handing back a plain string; `tests/fake_writer.py` now has a `FakeEnum` that behaves like the real thing.
- A hyperlink is `HyperLinkURL` + `HyperLinkTarget` on the run, and its navy underline comes from the `UnvisitedCharStyleName` / `VisitedCharStyleName` character styles ("Internet link" / "Visited Internet Link") — not from a colour. A plain replacement destroys all of it silently, so `read_runs` reports it and `replace_runs` restores it. Inline code is likewise a character style ("Source Text"), better carried over than imitated with a font.
- `setString` over a range holding several character runs **flattens it to one run**: four runs in, one out, so an inline monospace term and a coloured phrase both lose their look. Measured, not assumed. Reading the runs (`read_runs`) and writing them back with explicit per-run properties (`replace_runs`) is the only way text keeps its appearance through a rewrite; replacing run by run does not work reliably either, because setString takes its properties from the surrounding text.
- Paragraph borders are `TopBorder`/`BottomBorder`/`LeftBorder`/`RightBorder` with `*BorderDistance` — there is no `ParaTopBorder`, and guessing that name is a dead end. Consecutive paragraphs given the same border render as one box, since `ParaIsConnectBorder` defaults to true.
- A paragraph background cannot be set through `ParaBackColor`: writing it is silently ignored on a cursor *and* on the paragraph. `FillStyle = SOLID` plus `FillColor` **on the paragraph object** works, shows up afterwards as `ParaBackColor`, and survives saving. Ranges have no `FillStyle`, so the fill is applied per paragraph.
- For a code block prefer `apply_paragraph_style` with "Preformatted Text" over setting a font: the style carries the monospace font *and* the paragraph spacing, where `CharFontName` alone leaves body-text spacing. A style the document lacks throws inside UNO, so names are checked against `doc.StyleFamilies` first.
- `track_changes` on the mutating tools has three states, not two: omitted follows `doc.RecordChanges`, `True` records this edit anyway, `False` refuses to record it even in a recording document — and either override is undone afterwards so the owner keeps their setting. The result's `tracked` says what actually happened. A two-state version reported `tracked: false` while a recording document recorded the edit regardless, which is how a replacement turns up coloured with the original struck through.
- An undo context does **not** suppress redline recording — verified: `setString` with recording on yields 2 redlines whether or not it sits inside `enterUndoContext`/`leaveUndoContext`. Counting redlines is still no way to prove an edit was recorded when the paragraph already holds recorded edits: the new one merges into them and the count does not move.
- Spell checking works, grammar does not: create `com.sun.star.linguistic2.SpellChecker` **directly** (the one from `LinguServiceManager` resolves in pyuno to the `XSpellChecker1` overload wanting a numeric language id, and rejects any `Locale` with "Type 17 is not supported"). `getProofreader` is absent and the `Proofreader` service reports zero locales, so punctuation and grammar need LanguageTool installed as an extension.
- Writer picks the spelling dictionary from a run's `CharLocale`, so text written over text in another language is underlined word by word even when correct — `'Схемы'` checked as en-US is a "misspelling" with no suggestions. The replacement tools take a `language` tag and set the locale; `set_language` fixes what is already written. A paragraph's `createEnumeration()` yields text portions, each with its own `CharLocale`, which is how a run's real language is read.
- Mutations wrap the edit in `doc.UndoManager.enterUndoContext(...)` / `leaveUndoContext()` (the leave in a `finally`), so one assistant action is one Ctrl+Z, and check `doc.isReadonly()` first. `track_changes` defaults to **false**: with `RecordChanges = True` a replacement keeps the original struck through until accepted, which users read as the replacement having failed.
- `desktop.getCurrentComponent()` follows the focused frame and is **not always a document**: a modal dialog (including the extension's own status box) or the Start Center answers instead, supporting no document service and carrying no `Title`. `get_active_document()` therefore checks with `_is_document()` and falls back to `open_documents()[0]`; without that, every tool reported "not a Writer document" while one was open. Frames are not documents either — enumerate `getComponents()` and filter.
- Driving the plugin's SSE server from **one** out-of-process client over a single pyuno socket bridge is only reliable one call at a time; concurrent calls interleave and return each other's state. That is a property of the test rig, not of the plugin — in-process concurrent tool calls behave correctly. Keep `tests/live/*` and any SSE probe sequential.
- UNO objects can never be compared with `is`: pyuno mints a fresh proxy per call, so `hit.getText() is doc.getText()` is False even for a body-text hit. Compare ranges through `compareRegionStarts` instead, which works across proxies.
- **A comment is not text.** Writer represents one as *empty marker portions* — `Annotation` … `AnnotationEnd` around the commented range, or a lone `Annotation` for a point anchor — carrying the field in `TextField` and occupying zero characters, so offsets are unaffected. `read_runs` used to skip them as empty portions, so `replace_runs` destroyed them silently: one comment in, zero out. Comments now travel on the runs they cover (`comments`), `_flattening_loss` counts them, and `replace_runs` refuses when the range carries comments and none of the runs passed back does. Read them with `list_comments`, which anchors each to an address via `doc.getTextFields()`, and add one with `add_comment`.
- A comment covering several runs is reported on **each** of them, so summing the per-run lists counted one comment as three; `_distinct_comments` counts by identity instead. On the way back, `replace_runs` groups the consecutive runs carrying an equal comment and anchors it **once** over that whole stretch — anchoring per run would have turned one comment into three copies.
- A comment is named by its annotation's `Name` (`__Annotation__16442_3809372040`), which is the only stable way to point at one: author, text and anchor can all coincide. Writer names the comments made in its own interface, but an annotation created through the API comes back with an **empty** `Name` — and with a **zeroed** `DateTimeValue`, which shows in the margin as no date. `_anchor_comment` therefore stamps a date and names what Writer left unnamed (`__Annotation__mcp_<hex>`). Measured: a *range*-anchored comment does get a Name from Writer, a *point*-anchored one does not. An id survives saving and reopening the file, but not a rewrite that re-anchors the comment — `replace_runs` creates a new annotation, hence a new id.
- `list_comments` scopes by document, by section (`{"heading": N}` — the heading's paragraph plus everything under it, up to the next heading of the same or a higher level), by paragraph, by an exact range (a comment matches when its anchor overlaps, and a point anchor when it sits inside) or by the selection; a collapsed selection means the paragraph. `update_comment` writes `Content`/`Author`/`Resolved` and leaves the text alone; `delete_comment` takes the anchor's own text (`note.getAnchor().getText().removeTextContent(note)`), which removes the markers and keeps the commented text.
- Marker portions must be collected before they are interpreted: attaching a comment while walking the portions put a range comment in both the "open" and the "point" bucket and reported it twice. `_runs_in` therefore walks once into a list, works out each comment's span, then attaches by overlap; a lone `Annotation` never closed is the point anchor.
- An annotation is anchored **AS_CHARACTER**, so it counts as one position for cursor movement while adding no characters to the string: counting an offset with `goRight` from the paragraph start drifts by one per comment before it, which is how a comment on the second term of a paragraph came to sit over `" subscriptio"`. `_position_in` walks the text portions and moves only *inside* one — portions are split at every marker — so positions and characters stay in step. Every address in a paragraph that carries a comment depended on this.
- Rewriting a stretch that begins exactly where a comment's anchor **ends** swallows the `AnnotationEnd` marker and the comment with it — with `setString` and with `insertString(absorb=True)` alike. Beginning one character later keeps it, so `_plan_run_rewrite` starts such a stretch at `offset + 1` when that first character does not change, and gives up keeping the comment when it does. A stretch that *ends* where an anchor begins is harmless, and replacing the commented run itself leaves the comment as a point anchor. `doc.replaceAll` (Find & Replace) keeps comments properly.
- `replace_runs` therefore leaves alone every run that carries a comment and whose text has not changed, rewriting only the stretches that differ (right to left, so earlier offsets still hold). A translation that keeps the commented terms keeps their comments *whole* — id, date, author, language — where re-creating them loses all of that. The result reports `runs_kept`, `runs_rewritten`, `comments_kept` and `comments_written`, and the refusal counts only the comments on text that is actually changing.
- The language a comment's text is spell checked against is a **document-level** setting, not a property of the comment. Measured, in this order: it cannot be written on the annotation (its `TextRange` hands out a detached copy — a locale written through a cursor over it reads back from that cursor, is gone from the next enumeration, and leaves no trace in `content.xml`); it comes from the **"Comment" paragraph style**, taken when the note is *created*; writing a note's text again does not restamp it; and setting the style only for the moment of creation and putting it back afterwards fails, because the note then reports the language the style was put back to. So `set_comment_language` sets the style for the comments to come, `add_comment(language=...)` and `update_comment(language=...)` set it too and say so in `comment_language_set`, and changing an existing comment's language means making the comment again — `update_comment` reports `recreated` and `previous_id`.
- **A picture is not text either.** Writer shows one as an *empty portion of type `Frame`* at its anchor offset — for an inline (`AS_CHARACTER`) picture and a character-anchored (`AT_CHARACTER`) one alike — so it costs no characters and `read_runs` skipped it as an empty portion: nothing reported that a selection held a picture at all. Pictures now travel on the runs (`images`), `list_images` reports them by document, section, paragraph, range or selection with the address of the anchor and the text it is anchored to, and `export_image` writes one out through `com.sun.star.graphic.GraphicProvider.storeGraphic` (`inline=true` also returns it as an MCP image block, which `ai_interface` builds from `_image_content`).
- Replacing text **destroys an inline picture**: measured, the rewrite of the stretch that *begins* at the anchor offset kills it, while a stretch that *ends* there leaves it, and one starting a character later leaves it too. So a picture travels on the run that starts at its offset, `_plan_run_rewrite` keeps that run when its text is unchanged, and `replace_runs` refuses otherwise — a picture cannot be handed back through a tool call the way a comment can, since a `Graphic` does not fit in JSON. `_flattening_loss` counts them and `replace_range` names them in its refusal (`images_dropped` when `flatten=true`). An `AT_CHARACTER` picture survives a rewrite, its anchor moving to the start of the replaced stretch, so it is no reason to refuse one.
- **Selecting a picture leaves no text selection.** `controller.getSelection()` then hands back the picture *itself* — an `SwXTextGraphicObject` supporting `com.sun.star.text.TextGraphicObject`, with `getName()` and no `getCount` — where selecting text hands back an `SwXTextRanges` collection. Every selection-based tool therefore failed with "the selection is not a text range: getCount", and `get_cursor_info` with "no text selection" from `unotxvw.cxx`, which left a caller unable to say which of two pictures was in front of it. `_selected_graphics` reads it (a multi-shape selection comes as a collection to filter): `list_images({"selection": true})` reports the selected picture with `scope: {"selection": "picture"}`, `export_image` with no name writes it (`was_selected`), `get_cursor_info` answers `selection_kind: "picture"` with the picture described, and the text tools refuse by *naming* what is actually selected.
- A picture's own name (`Name`) is how a caller points at one; `Title` and `Description` are the title and the alternative text; `Width`/`Height` are the frame in 1/100 mm, while `Graphic.SizePixel` is the picture's own resolution and `Graphic.MimeType` its type (`image/x-vclgraphic` means "whatever LibreOffice holds in memory", not a file type). `GraphicURL` throws on read — do not reach for it. A picture *can* be put back from its `Graphic` with its size, title and alternative text, which is how a restore would work if one is ever wanted.
- A style's **own definition** is readable through `getPropertyState`: `DIRECT_VALUE` for a property the style sets, `DEFAULT_VALUE` for one it inherits. For "Text body" that is 8 properties of 195, and they match its `<style:style>` element in `styles.xml` exactly — so `describe_style` answers "what is this style" from the running document, and nobody needs to unzip the file to find out. It reports `set_here` (the definition, values in mm/pt/percent with the raw number kept), `effective` (a curated set of what is in force, each saying `this style` or `inherited`), the parent chain, `FollowStyle`, `isUserDefined()`/`isInUse()` — which are **methods**, not properties, unlike `IsAutoUpdate` and `Hidden` — and every property with its state under `all_properties`. `DisplayName` is the *UI* name ("Body Text"), which is not the `style:display-name` in the file ("Text body").
- Three measured facts shape the document-level tools. `storeAsURL` with **no `FilterName` writes ODF whatever the file is called**: a document "saved as .docx" came out as ODF with a `.docx` name (`mimetype: application/vnd.oasis.opendocument.text`), which is worse than a refusal, so `save_document` picks the filter from the extension (`WRITER_SAVE_FILTERS`), refuses an extension it does not know, and sends `pdf` to `export_document` — `storeAsURL` with a PDF filter would leave the document claiming to *be* a PDF. `storeAsURL` is Save As, not a copy: the document goes on living at the new URL, where `storeToURL` (which `export_document` uses) leaves it where it was.
- `doc.close(True)` closes a **modified** document without a murmur and the changes are gone — no dialog, no veto. So `close_document` refuses a document with unsaved changes unless `unsaved` says `"save"` or `"discard"`, refuses `"save"` for a document that has never been saved, and leaves the document open if the save fails rather than closing it anyway.
- **UNO has no rename.** `storeAsURL` under a new name leaves the old file exactly where it was — both files afterwards — and LibreOffice writes a fresh `.~lock.<name>#` beside the new one. `rename_document` therefore keeps the old file unless `delete_original=true`, in which case it also removes the stale lock of the old name, and it says in the result which happened. A bare name keeps the document's directory; a name with no extension keeps its format. `os.unlink` is the standard library, not an external program, so this stays within the constraint above.
- Text is addressed one way: `{"paragraph": i, "offset": k, "length": n}` (body paragraphs, tables skipped) or `{"selection": true}`. `_locate_range` produces an address from a range, `_resolve_address` turns one back into a range, and every tool goes through them — see `docs/superpowers/specs/2026-08-18-writer-text-tools-design.md`.
- `tests/live/writer_tools_check.py` checks the bridge against a real headless LibreOffice. Run it with `/usr/bin/python3` (the venv has no `uno`) whenever bridge code changes; a green pytest run alone does not mean the UNO calls work.

## Conventions

- Structured returns: the external server uses Pydantic models (`DocumentInfo`, `TextContent`, `ConversionResult`, `SpreadsheetData`) so MCP clients get schemas; the plugin returns plain dicts because Pydantic isn't available there.
- Root `mcp-helper.sh` and `generate-config.sh` are one-line `exec` wrappers around `scripts/`.
- `docs/` is extensive and largely aspirational — verify claims against code before relying on them.
