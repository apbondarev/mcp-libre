## Architecture

Two **independent** MCP server implementations live here. They share no code; a change in one is not a change in the other.

### 1. External server — `src/libremcp.py` (14 tools, stdio)

A single-file FastMCP server that manipulates documents **as files on disk**, driving LibreOffice through `subprocess` (`libreoffice --headless --convert-to ...`). It never talks to a running LibreOffice instance, so it has no concept of the active document, the cursor, or the selection.

Consequences worth knowing before adding a tool:

- `_run_libreoffice_command` tries `libreoffice`, `loffice`, `soffice` in order.
- Text extraction (`read_document_text`) converts to `.txt` in a temp dir, then falls back to unzipping `content.xml` (`_extract_text_from_odt`), then to reading raw bytes.
- **Editing is destructive by design.** `insert_text_at_position` reads all text, concatenates, and *recreates* the file (`_recreate_writer_document` → LibreOffice conversion → `_create_minimal_odt` hand-written ODT zip). All formatting, styles, and images are lost. A `.backup` copy is restored on failure. `_insert_text_writer_document` is dead code — it builds a UNO macro string and then `return False` unconditionally.
- Resources: `documents://` (rglob over `~/Documents`, `~/Desktop`, cwd) and `document://{path}`.
- `main()` handles `--test`, `--help`, `--version` before `mcp.run()`; startup chatter goes to stderr so stdio JSON-RPC stays clean.

Entry points: `src/main.py` does a flat `import libremcp`, which works only because Python puts the script's own directory on `sys.path` — hence `PYTHONPATH=<repo>/src` in the config templates. The root `libremcp.py` is a 6-line vestigial stub, not the server; `pyproject.toml`'s `[project.scripts]`/hatch `packages` still point at stale paths.

### 2. Embedded plugin — `plugin/pythonpath/` (108 tools, SSE over HTTP :8765)

Runs *inside* LibreOffice via UNO, so it acts on live open documents with no file I/O. Four layers:

- `registration.py` — the UNO component. Registered as a `com.sun.star.frame.ProtocolHandler` (see `ProtocolHandler.xcu`) for the `org.mcp.libreoffice.extension:` protocol; `Addons.xcu` menu items dispatch URLs like `...:start_mcp_server` into `MCPExtension._execute_action`. Server state lives in module-level globals shared across instances; start/stop run on daemon threads.
- `ai_interface.py` — MCP SSE transport on a `BaseHTTPRequestHandler`: `GET /sse` opens a stream and mints a session, `POST /messages?sessionId=` accepts JSON-RPC whose replies are pushed back over that session's queue. Also `GET /health`, `/`, `/tools` for debugging. Implements `initialize`, `tools/list`, `tools/call`, `ping` by hand (protocol version `2024-11-05`).
- `mcp_server.py` — `LibreOfficeMCPServer` (lazy singleton via `get_mcp_server()`), a `self.tools` dict of `{description, parameters (JSON Schema), handler}` plus thin `*_live` handlers.
- `uno_bridge.py` — the only place that touches UNO objects (`Desktop`, `XTextDocument`, `XSpreadsheetDocument`, `PropertyValue`).

**Adding a plugin tool means three edits**: a `UNOBridge` method, a `*_live` handler, and a `self.tools[...]` entry in `_register_tools` (the JSON Schema there is what clients see — `execute_tool` splats it as `**parameters`).

Hard constraints on plugin code:

- **No external programs. A tool must work with nothing but LibreOffice and the Python standard library, on any machine where LibreOffice runs.** No `pdftoppm`, no ImageMagick, no `gs`, no screenshot utility — a capability that needs one of those is not a capability of this server. Whatever is wanted is either reachable through UNO (a filter, `XRenderable`, `GraphicProvider`) or it is not offered at all. This is a requirement on every tool, not a preference: the server is installed as a LibreOffice extension on machines whose contents nobody controls.
- It runs under LibreOffice's bundled Python: **stdlib only**. No `pip` deps, no `mcp`, no `httpx`, no `pydantic`. That's why the SSE transport and JSON-RPC are hand-rolled.
- Errors are returned as `{"success": False, "error": ...}` dicts rather than raised, since exceptions inside UNO callbacks vanish.
- **Never do UNO work on a thread of your own while the main thread shows a modal dialog.** A dialog runs a nested event loop holding the SolarMutex; a Python thread cannot acquire it, and the process dies with no traceback — `/tmp/mcp_extension.log` simply stops. This crashed LibreOffice on "Start MCP Server" until `_execute_action` was made synchronous. UNO from an HTTP handler thread is fine while the main thread sits in its normal event loop, which is why tool calls work.
- `AIInterface.stop()` signals open SSE sessions *before* `shutdown()`/`server_close()`, and `MCPHTTPServer` sets `daemon_threads = True`. Without both, one open stream blocks shutdown forever, because `server_close()` joins non-daemon handler threads.
- `MCP_EXTENSION_LOG` overrides the log path, which is how tests avoid appending to the file you are tailing.
- `plugin/description.xml` `identifier`/`version` must stay in sync with the hardcoded `org.mcp.libreoffice.extension` in `install.sh` and `build.sh`'s `VERSION`. `META-INF/manifest.xml` names only the **UNO component** (`pythonpath/registration.py`) and the two `.xcu` files; `build.sh` zips the whole `pythonpath/` directory, so a new module beside the others needs no manifest entry.
- The plugin is one object per side, in several files. `uno_bridge.py` is a facade: `UNOBridge` is assembled from mixins, one per subject — `uno_values` (no documents at all), `uno_address`, `uno_anchors`, `uno_documents`, `uno_view`, `uno_reading`, `uno_editing`, `uno_formatting`, `uno_runs`, `uno_comments`, `uno_fields`, `uno_bookmarks`, `uno_references`, `uno_indexes`, `uno_notes`, `uno_sections`, `uno_headers`, `uno_layout`, `uno_links`, `uno_surgery`, `uno_direct`, `uno_stylewriting`, `uno_history`, `uno_convert`, `uno_redlines`, `uno_tables`, `uno_images`, `uno_spelling`, `uno_rendering` — and its docstring is the map. `mcp_server.py` is the same: dispatch and the registry live there, while each tool sits beside its subject in `mcp_<subject>_tools.py`, contributing `_register_<subject>()`. The parts call each other only through `self`, and nothing imports from `uno_values` backwards, which is what lets them sit apart. **Adding a tool is still three edits**: a bridge method in its part, a `*_live` handler in its part of the server, and the `self.tools[...]` entry beside that handler.
- **`isinstance` never works on UNO objects.** Every proxy is `<class 'pyuno'>` and inherits none of the imported `com.sun.star.*` interfaces, so `isinstance(doc, XTextDocument)` is always False — silently, since the fallback branch just reports "unknown". Use the `_supports(obj, service)` helper in `uno_bridge.py` with a service name instead. This defect had disabled `get_text_content`, `insert_text`, `format_text` and every document-type report until it was fixed.
- A text range belongs to the text that owns it. Inside a table cell or a frame that is *not* `doc.getText()`, and passing a foreign range to the body text throws "End of content node doesn't have the proper start node" — so build cursors from `range.getText()`, as `get_cursor_info` does.
- `insertString(cursor, text, bAbsorb)` — the last flag decides insert vs replace. `insert_text` passes `False`, so with a selection it inserts at the selection start and leaves the original: that is why "translate and replace" produced both texts. `replace_selection` rewrites the resolved range with `setString` instead.
- Every mutation goes through `_guarded_edit(doc, undo_title, track_changes, edit)`: read-only refusal, one undo context, the three-state recording contract, and the document's own setting restored. Add a mutating tool by writing the `edit` closure, not by repeating the guards.
- `replace_range`/`replace_selection` **refuse** a range holding more than one run, or any hyperlink, unless `flatten=true`: replacing such a range with one string destroys inline code, italics and links, and the tool can see that before writing. `read_runs` + `replace_runs` is the route that keeps them. A character style on a *single* run survives a flat replacement, so that alone is not a refusal — measured, along with the fact that a link does not survive even as the only run.
- A pyuno enum stringifies as `<Enum instance com.sun.star.awt.FontSlant ('ITALIC')>`, so read its `.value`. Testing `str(...)` reported every run as upright, and the fakes hid it by handing back a plain string; `tests/fake_writer.py` now has a `FakeEnum` that behaves like the real thing.
- A hyperlink is `HyperLinkURL` + `HyperLinkTarget` on the run, and its navy underline comes from the `UnvisitedCharStyleName` / `VisitedCharStyleName` character styles ("Internet link" / "Visited Internet Link") — not from a colour. A plain replacement destroys all of it silently, so `read_runs` reports it and `replace_runs` restores it. Inline code is likewise a character style ("Source Text"), better carried over than imitated with a font.
- `setString` over a range holding several character runs **flattens it to one run**: four runs in, one out, so an inline monospace term and a coloured phrase both lose their look. Measured, not assumed. Reading the runs (`read_runs`) and writing them back with explicit per-run properties (`replace_runs`) is the only way text keeps its appearance through a rewrite; replacing run by run does not work reliably either, because setString takes its properties from the surrounding text.
- Paragraph borders are `TopBorder`/`BottomBorder`/`LeftBorder`/`RightBorder` with `*BorderDistance` — there is no `ParaTopBorder`, and guessing that name is a dead end. Consecutive paragraphs given the same border render as one box, since `ParaIsConnectBorder` defaults to true.
- A paragraph background cannot be set through `ParaBackColor`: writing it is silently ignored on a cursor *and* on the paragraph. `FillStyle = SOLID` plus `FillColor` **on the paragraph object** works, shows up afterwards as `ParaBackColor`, and survives saving. Ranges have no `FillStyle`, so the fill is applied per paragraph.
- For a code block prefer `apply_paragraph_style` with "Preformatted Text" over setting a font: the style carries the monospace font *and* the paragraph spacing, where `CharFontName` alone leaves body-text spacing. A style the document lacks throws inside UNO, so names are checked against `doc.StyleFamilies` first.
- `track_changes` on the mutating tools has three states, not two: omitted follows `doc.RecordChanges`, `True` records this edit anyway, `False` refuses to record it even in a recording document — and either override is undone afterwards so the owner keeps their setting. The result's `tracked` says what actually happened. A two-state version reported `tracked: false` while a recording document recorded the edit regardless, which is how a replacement turns up coloured with the original struck through.
- An undo context does **not** suppress redline recording — verified: `setString` with recording on yields 2 redlines whether or not it sits inside `enterUndoContext`/`leaveUndoContext`. Counting redlines is still no way to prove an edit was recorded when the paragraph already holds recorded edits: the new one merges into them and the count does not move.
- Spell checking works, grammar does not: create `com.sun.star.linguistic2.SpellChecker` **directly** (the one from `LinguServiceManager` resolves in pyuno to the `XSpellChecker1` overload wanting a numeric language id, and rejects any `Locale` with "Type 17 is not supported"). `getProofreader` is absent and the `Proofreader` service reports zero locales, so punctuation and grammar need LanguageTool installed as an extension.
- Writer picks the spelling dictionary from a run's `CharLocale`, so text written over text in another language is underlined word by word even when correct — `'Схемы'` checked as en-US is a "misspelling" with no suggestions. The replacement tools take a `language` tag and set the locale; `set_language` fixes what is already written. A paragraph's `createEnumeration()` yields text portions, each with its own `CharLocale`, which is how a run's real language is read.
- Mutations wrap the edit in `doc.UndoManager.enterUndoContext(...)` / `leaveUndoContext()` (the leave in a `finally`), so one assistant action is one Ctrl+Z, and check `doc.isReadonly()` first. `track_changes` defaults to **false**: with `RecordChanges = True` a replacement keeps the original struck through until accepted, which users read as the replacement having failed.
- `desktop.getCurrentComponent()` follows the focused frame and is **not always a document**: a modal dialog (including the extension's own status box) or the Start Center answers instead, supporting no document service and carrying no `Title`. `get_active_document()` therefore checks with `_is_document()` and falls back to `open_documents()[0]`; without that, every tool reported "not a Writer document" while one was open. Frames are not documents either — enumerate `getComponents()` and filter.
- A second pyuno client talking to the same office while the server holds its bridge is the arrangement the next point warns about, and it does not merely interleave: an assistant's own dump script **segfaulted** against the live office (exit 139, core dumped) while the server was connected. The office and the document survived; the script did not. Tools exist so that nothing has to open a second bridge.
- **Every tool that acts on a document takes `document`.** Four did not — `insert_text`, `format_text`, `export_document`, `get_text_content` — and two of those write, so they went to whatever `getCurrentComponent()` answered: that is how a call meant for a scratch document reached the user's own while a check was running (it wrote nothing, and only because an earlier call in the same script had failed first). `get_document_info` and `get_cursor_info` take it too now, which leaves exactly `create_document_live` and `list_open_documents` without one, since neither has a document to be pointed at — and `tests/test_document_targeting.py` holds that line. `format_text_live` was `**kwargs`, which is why the drift test could not see that its schema promised five parameters the handler never named; it takes them explicitly now.
- **A field is the mirror image of a comment.** Measured: a field is a portion of type `TextField` that **carries the text it shows** — 7 characters for a date — while costing *one position* for cursor movement, where a comment's markers carry no characters and cost one position. Three things follow, all of them found by building the tools. `_position_in` skipped every non-Text portion, so every address after a date came out seven characters to the right; it counts a field's characters now and clamps to the field's start when an offset falls inside one, since no cursor can stand in the middle of a date. A zero-width cursor standing *at* a field's position hands back the text the field shows, so string arithmetic around a field lies: a date at the start of a paragraph measured itself as seven characters in, which is why `list_fields` takes its offsets from a walk of the portions instead. And `_match_in` now measures a hit's offset backwards from its start, the way `_locate_range` does, so a search hit and a located range agree.
- The service to create one is `com.sun.star.text.TextField.<kind>` with a **capital T**: the lower-case `textfield` spelling answers for some kinds and then throws from `editeng` on insertion, because it hands back the drawing layer's field rather than Writer's. `getPresentation(False)` is what a field shows, `getPresentation(True)` the command Writer names it by. A **comment is a text field too**, so anything walking `getTextFields()` has to leave the annotations out or every note in the margin turns up as a field. A page-number field asks for `SubType = CURRENT` or it shows the previous page — 0 on the first one — and a page number reads 0 until the fields are refreshed. `doc.getTextFields().refresh()` is F9.
- A field has no id, so `delete_field` names one by where it sits; an address covering several is refused unless it matches one of them exactly, which is what makes a field showing *nothing* — a title the document has not got — possible to remove at all. Rewriting a range that holds a field destroys it and leaves the text behind, so `read_runs` reports `field` on the run that is one, `_flattening_loss` counts them, and `replace_range` refuses unless `flatten` accepts it and then says `fields_dropped`.
- **A recorded change marks its text the way a comment does**: empty portions of `TextPortionType == "Redline"` around it, carrying `RedlineType`, `RedlineAuthor` and `RedlineIdentifier`, with `IsStart` saying which end this is — measured. So the runs can say which of them a change covers (`changes` on every run), `_distinct_changes` counts them once each, and the flatten guard counts them beside the comments and the pictures. Before that they looked like ordinary runs, and a rewrite took them away silently: measured, two changes in and none out, with the struck-out **deletion back in the document as live text** — a translation would have resurrected the words a reviewer had cut. `replace_range`/`replace_selection` name them in the refusal and report `changes_dropped` under `flatten=true`; `replace_runs` refuses outright unless `flatten=true`, because a change cannot be handed back the way a comment can — it is Writer's own bookkeeping — and the refusal points at `accept_tracked_changes` / `reject_tracked_changes`, which are the route that keeps the record. The guard sees the changes marked *inside* the paragraph it is given: an insertion of a whole paragraph opens its marker at the end of the paragraph before, so reading that next paragraph alone does not show it. A safety net, not a proof.
- **A table's shape is changed through its rows and columns, and sorting is not.** Measured: `table.getRows().insertByIndex(index, count)` puts rows *before* the 0-based index and `removeByIndex` takes them from it, the same for `getColumns()`; a merge is `createCursorByCellName("A1")` + `gotoCellByName("B2", True)` + `mergeRange()`, after which the merged cell holds every text that was in the rectangle joined by line breaks and the cells that went are gone from `getCellNames()`; and `splitRange(count, horizontal)` takes the number of *extra* cells, where `horizontal=True` divides a cell by a horizontal line — stacking the new cells in **rows** — which reads like the opposite of what the flag is called.
- **`XSortable.sort` on a Writer table honours only the descriptor it made itself.** Measured four ways: the descriptor from `createSortDescriptor()` passed straight back sorts by column 1, and *any* rebuilt sequence — even one naming column 1 exactly as the default does, built from `uno.createUnoStruct("com.sun.star.table.TableSortField")` with every property the original carried — is ignored **silently**, the table left as it was. Iterating the sequence yields copies, so mutating a `PropertyValue` in place changes nothing either; what looked like a working sort was the default doing its own thing. So `sort_table` works the order out itself and writes the cells back: heading rows stay put (the table's `HeaderRowCount` unless told otherwise), a merged table is refused since whole rows cannot move while cells are joined, and a cell holding more than one run is refused unless `flatten` accepts the flattening that writing it back would cost. What moves is the text: a cell's background and paragraph style stay where they are, so banding stays banded.
- **A recorded change is a property set, and settling one goes through the dispatcher.** Measured: `doc.getRedlines()` hands out redlines carrying `RedlineType` ("Insert", "Delete", "Format"), `RedlineAuthor`, `RedlineDateTime`, `RedlineComment`, `RedlineDescription` (Writer's own sentence, in the UI's language), `RedlineIdentifier` and `RedlineStart`/`RedlineEnd`, which are ranges — while the redline's own `getString()` **throws** (`unoredline.cxx:531`), so the text of a change is read by walking a cursor between its ends. The author is the office's user name; `doc.Author` does not exist. There is **no accept or reject on the model** (`acceptAllRedlines` and friends are absent): a change is settled by selecting it and sending `.uno:AcceptTrackedChange` / `.uno:RejectTrackedChange` through `com.sun.star.frame.DispatchHelper`, or the whole lot with `.uno:AcceptAllTrackedChanges` / `.uno:RejectAllTrackedChanges` — verified headless, three redlines to none with the text left as the decision says.
- `list_tracked_changes` scopes like `list_comments` and narrows by `author`; `accept_tracked_changes` / `reject_tracked_changes` pick their changes in exactly one way — `change_id`, `author`, `address` or `all` — and refuse to guess when none or two are given. They work from the last change to the first, finding each again by its identifier because settling one moves the text after it, and they put the reader's own selection back when they are done. The whole call is one undo step. What a dispatch does to the *text* is LibreOffice's business, so the fakes model only the bookkeeping (`tests/uno_stubs.py`'s `FakeDispatchHelper`) and the text effect is proved in the live harness.
- **A reply is a comment joined to its parent by `ParentName`.** Measured: an annotation carries `ParentName` (empty for a top-level comment), writing it makes the note a reply, and it survives saving as `loext:parent-name`; `ParaId`/`ParaIdParent` sit beside it for OOXML. A reply anchored on `parent.getAnchor()` hits the same "no SwTextAttr inserted?" as a selection does, so it goes through `_anchor_comment`, which walks the cursor. Writer accepts a reply to a reply, so a thread is a chain rather than two levels. `add_comment(reply_to=…)` takes no address — the reply sits on its parent's own anchor — and `list_comments` reports `reply_to` and `replies` per comment with `threads`/`replies` counted.
- **`Resolved` belongs to each annotation on its own.** Measured: marking a parent leaves its replies unresolved, and Writer then shows half a settled thread. `resolve_comments` therefore takes the replies of whatever it picks along with it, and says how many followed. It and `delete_comment` pick their comments the way the review tools pick changes — `comment_id`, `author`, `address` or `all`, one way only — and `list_comments` narrows by `author` and by `resolved`, reporting `unresolved` and the authors beside the counts. Deleting is refused only when it would actually orphan a reply: with `all` nothing is left behind, so there is nothing to refuse. An annotation that has been removed no longer answers with its own `Name`, so what is deleted is named before anything goes.
- Two ways a thread came apart, both now refused or repaired. **Deleting a parent leaves its replies behind**, still naming a comment that is no longer in the document — Writer says nothing and the margin shows orphans; `delete_comment` refuses unless `with_replies=true`, and then removes the thread from the leaves inward. And **re-anchoring a comment gives it a new id**, so a reply written beside it named the old one: `replace_runs` keeps a map of old id to new and joins the threads again after the writes, while `update_comment(language=…)` — which must make the note again — re-points its replies and reports `replies_repointed`. A four-note thread through a rewrite of the text it sits on comes out as one thread of four, checked live.
- The fakes were wrong about comments in two ways the threads exposed. `insert_comment` rebuilt a paragraph's portions from its plain text, so a second comment over the same words **destroyed the first** — a reply came back as the only comment in the document; it now threads the markers into the portions that are there. And an opening `Annotation` marker was treated as surviving unless *strictly* inside the replaced span, where the arithmetic is that of a half-open range: a marker dies when it sits in the characters that go, start included and end excluded. Measured live — rewriting the commented word destroys its comment outright, leaving `replace_runs` to write the one new note rather than a duplicate.
- **Every result says what it cost, and every refusal says why in a word.** A refusal used to be a sentence of English, so a caller could only match on it: `_run_tool` — the one place every call goes through, tool calls and batch steps alike — now stamps `elapsed_ms` on every result and `code` on every refusal that named none. The set is closed and small, `uno_values.ERROR_CODES`: `NO_DOCUMENT`, `WRONG_DOCUMENT_TYPE`, `READ_ONLY`, `INVALID_ADDRESS`, `NOT_FOUND`, `INVALID_PARAMETER`, `WOULD_LOSE_FORMATTING`, `UNSUPPORTED`, `FAILED`. A code earns its place only when a caller would do something different about it, `refusal(code, message, **extra)` raises on a code nobody declared, and `tests/test_result_contract.py` fails if a code appears in the source that `ERROR_CODES` does not hold, or if any tool answers a refusal without one. A batch reports the code of the step that failed, not a code of its own. `elapsed_ms` exists because a slow tool was a thing only a human with a stopwatch could see — `find_text` took ten seconds for twenty hits and nothing in its answer said so.
- **The client is told how to use this server before its first call.** `mcp_guide.INSTRUCTIONS` — the address forms, the refusals and the way round each, what is not text, the language rule, batching — goes out as the `instructions` of the MCP `initialize` result (4058 characters, about 650 words, delivered in a millisecond), because everything measured here lives in this file, where an assistant driving the server over MCP never sees it. The same text is the body of `skills/libreoffice-mcp/SKILL.md`, written by `scripts/write_skill.py` from that one constant, so the two cannot drift; `tests/test_guide.py` fails when the checked-in skill is stale, when the guide names a tool this server does not register, and when `initialize` stops carrying it. The skill is deliberately **not** installed into `~/.claude/skills` by the server: that is the user's directory, and the name `libreoffice-writer` is already taken there by a skill about driving LibreOffice from the command line — hence `libreoffice-mcp`.
- **Undo contexts nest, and only the outermost is an entry.** Measured: three edits, each wrapped in a context of its own by `_guarded_edit`, run inside one outer context leave a *single* entry carrying the outer title, one Ctrl+Z takes all three back, and redo puts them all back. A context that writes nothing leaves **no** entry at all. That is what `batch_live` stands on: `open_undo_group` / `close_undo_group` around a list of `{tool, parameters}` steps, so a plan an assistant carries out is one edit to the reader instead of twelve. Every step is checked before any runs — the tool must exist, it must not be another batch, its parameters must be an object, and it must not name a different document, since one batch is one document's undo step — but a step can still fail on the document, and `on_error` says what then: `stop` (the default), `continue`, or `undo`, which takes the whole batch back.
- **Counting undo entries is no way to tell whether something was written**: Writer's undo stack has a limit, and on a full one a new entry pushes the oldest out while the count stays put — which is how a failed batch first went untaken-back on a long session. `undo_group` watches the *top* of the stack as well as its size, and undoes nothing when neither moved, since a bare `undo()` would then take back whatever the reader did before the batch began.
- Measured on a real translation through the server: the same section, one `batch_live` instead of twelve `replace_runs_live` calls, went from 33 requests and 6.61s to **22 requests and 4.30s** — and from twelve entries in the Undo menu to one. A step cannot read another step's result, so a batch is for a plan already worked out, not for a search followed by what the search found.
- **A tool must not sweep the document to answer about one paragraph.** `read_runs` cost 0.54–1.15s a call on a 300-paragraph document with 11 tables and 2 pictures, and `list_tables` 1.0s (2.3s on a real one), because three habits each walked the whole body: `_range_spans` compared the range against *every* paragraph and table (six UNO calls apiece), `_images_in` **described** every picture in the document — and describing one works out its anchor's address, another walk — and `_describe_table` asked `_paragraphs_before_table` per table, a walk each. All three are now answered without the walk where the answer cannot depend on it: a range inside a table cell spans no body paragraph and no table; a range inside **one** paragraph holds no table either, since a table sits *between* paragraphs (`_within_one_paragraph`, four UNO calls); a picture's anchor is compared with the paragraph before it is described; and `_table_positions` places every table in a single walk. Measured after: read_runs 0.012s / 0.081s / 0.180s at paragraphs 5 / 150 / 290, list_tables 0.24s, `replace_range` over part of a paragraph 0.63s → 0.09s. A real translation of a thirteen-paragraph section through the MCP server went from 15.17s to 6.61s over the same 33 requests.
- **A block address was answered by comparing it with the whole document.** Measured on a real 6981-paragraph guide: `read_runs` over **one** paragraph cost 1.4–1.9s and over **two** 23–24s — thirteen times the work for twice the text — because `_note_what_is_out_of_reach` asks `_range_spans` what a range covers, and that walks the body comparing regions against every paragraph and every table (six UNO calls apiece) for anything not inside one paragraph. A single paragraph had been given the `_within_one_paragraph` short cut; a block had nothing. But a block **names its own paragraphs**, so there is nothing to compare: `_spans_of_block` takes them from the address and only the tables standing between them have to be found — and `_runs_across` now collects those in the walk it was making anyway, where `_table_positions` would have been a second sweep of the whole document. `_formulas_across` does the same for the formulas, which on a guide holding **one** formula cost a 4.0s placing sweep per call. Measured after: two paragraphs 23–24s → 1.55–1.77s, one paragraph 1.4–1.9s → 0.6–0.7s, ten paragraphs 31–47s → 7.6–23s. What is left is the cost of *reaching* paragraph N by walking to it — two paragraphs at 6500 are still ~10s, and that is what an anchor, which remembers its index, avoids.
- Resolving `{"paragraph": N}` walks the body to reach that paragraph, and `_locate_range` then walked it again to work out the index it had just been given. `_paragraph_hint(address, doc)` hands it forward instead, which is the rest of the cost above. An anchor names no number, so it **remembers** the paragraph it was last found in and checks that memory — reaching that paragraph and asking whether it starts where the anchor does — falling back to the walk on a miss; that makes reading by anchor no dearer than reading by index, and at paragraph 290 cheaper (0.11s against 0.18s).
- `find_text` used to address each hit on its own, and each of those walked the body from the start: **0.85s per hit** over a socket on a 500-paragraph document, ten seconds for twenty hits. `findAll` returns matches in document order, so one sweep now hands each its paragraph — two UNO calls per paragraph, since every call crosses the bridge — and a match the sweep cannot place (one inside a table cell, which compares against the body without complaint and then refuses a cursor from it) falls back to the slow path that knows cell addresses. A range whose text *is* a cell no longer searches the body at all before looking at the tables. Twenty hits with ten paragraphs of context each: 0.76s, down from 9.5s.
- A hit alone is half an answer — `find_text` takes `paragraphs_before` and `paragraphs_after`, and brings them with their indices and styles, which is the call a caller would otherwise make next for every hit.
- Formatting a document a call at a time is what sends an assistant off to write such a script: syntax colouring is one span per token, so a code block is twenty calls and twenty undo steps. `format_ranges` takes the list, checks every address first, and applies them in one guarded edit — nothing is written if any entry is wrong, and character formatting changes no text, so the addresses stay true as it goes.
- Driving the plugin's SSE server from **one** out-of-process client over a single pyuno socket bridge is only reliable one call at a time; concurrent calls interleave and return each other's state. That is a property of the test rig, not of the plugin — in-process concurrent tool calls behave correctly. Keep `tests/live/*` and any SSE probe sequential.
- UNO objects can never be compared with `is`: pyuno mints a fresh proxy per call, so `hit.getText() is doc.getText()` is False even for a body-text hit. Compare ranges through `compareRegionStarts` instead, which works across proxies.
- **A comment is not text.** Writer represents one as *empty marker portions* — `Annotation` … `AnnotationEnd` around the commented range, or a lone `Annotation` for a point anchor — carrying the field in `TextField` and occupying zero characters, so offsets are unaffected. `read_runs` used to skip them as empty portions, so `replace_runs` destroyed them silently: one comment in, zero out. Comments now travel on the runs they cover (`comments`), `_flattening_loss` counts them, and `replace_runs` refuses when the range carries comments and none of the runs passed back does. Read them with `list_comments`, which anchors each to an address via `doc.getTextFields()`, and add one with `add_comment`.
- A comment covering several runs is reported on **each** of them, so summing the per-run lists counted one comment as three; `_distinct_comments` counts by identity instead. On the way back, `replace_runs` groups the consecutive runs carrying an equal comment and anchors it **once** over that whole stretch — anchoring per run would have turned one comment into three copies.
- A comment is named by its annotation's `Name` (`__Annotation__16442_3809372040`), which is the only stable way to point at one: author, text and anchor can all coincide. Writer names the comments made in its own interface, but an annotation created through the API comes back with an **empty** `Name` — and with a **zeroed** `DateTimeValue`, which shows in the margin as no date. `_anchor_comment` therefore stamps a date and names what Writer left unnamed (`__Annotation__mcp_<hex>`). Measured: a *range*-anchored comment does get a Name from Writer, a *point*-anchored one does not. An id survives saving and reopening the file, but not a rewrite that re-anchors the comment — `replace_runs` creates a new annotation, hence a new id.
- `list_comments` scopes by document, by section (`{"heading": N}` — the heading's paragraph plus everything under it, up to the next heading of the same or a higher level), by paragraph, by an exact range (a comment matches when its anchor overlaps, and a point anchor when it sits inside) or by the selection; a collapsed selection means the paragraph. `update_comment` writes `Content`/`Author`/`Resolved` and leaves the text alone; `delete_comment` takes the anchor's own text (`note.getAnchor().getText().removeTextContent(note)`), which removes the markers and keeps the commented text.
- Marker portions must be collected before they are interpreted: attaching a comment while walking the portions put a range comment in both the "open" and the "point" bucket and reported it twice. `_runs_in` therefore walks once into a list, works out each comment's span, then attaches by overlap; a lone `Annotation` never closed is the point anchor.
- An annotation is anchored **AS_CHARACTER**, so it counts as one position for cursor movement while adding no characters to the string: counting an offset with `goRight` from the paragraph start drifts by one per comment before it, which is how a comment on the second term of a paragraph came to sit over `" subscriptio"`. `_position_in` walks the text portions and moves only *inside* one — portions are split at every marker — so positions and characters stay in step. Every address in a paragraph that carries a comment depended on this.
- Rewriting a stretch that begins exactly where a comment's anchor **ends** swallows the `AnnotationEnd` marker and the comment with it — with `setString` and with `insertString(absorb=True)` alike. Beginning one character later keeps it, so `_plan_run_rewrite` starts such a stretch at `offset + 1` when that first character does not change, and gives up keeping the comment when it does. A stretch that *ends* where an anchor begins is harmless, and replacing the commented run itself leaves the comment as a point anchor. `doc.replaceAll` (Find & Replace) keeps comments properly.
- `replace_runs` therefore leaves alone every run that carries a comment and whose text has not changed, rewriting only the stretches that differ (right to left, so earlier offsets still hold). A translation that keeps the commented terms keeps their comments *whole* — id, date, author, language — where re-creating them loses all of that. The result reports `runs_kept`, `runs_rewritten`, `comments_kept` and `comments_written`, and the refusal counts only the comments on text that is actually changing.
- The language a comment's text is spell checked against is a **document-level** setting, not a property of the comment. Measured, in this order: it cannot be written on the annotation (its `TextRange` hands out a detached copy — a locale written through a cursor over it reads back from that cursor, is gone from the next enumeration, and leaves no trace in `content.xml`); it comes from the **"Comment" paragraph style**, taken when the note is *created*; writing a note's text again does not restamp it; and setting the style only for the moment of creation and putting it back afterwards fails, because the note then reports the language the style was put back to. So `set_comment_language` sets the style for the comments to come, `add_comment(language=...)` and `update_comment(language=...)` set it too and say so in `comment_language_set`, and changing an existing comment's language means making the comment again — `update_comment` reports `recreated` and `previous_id`.
- **A picture is not text either.** Writer shows one as an *empty portion of type `Frame`* at its anchor offset — for an inline (`AS_CHARACTER`) picture and a character-anchored (`AT_CHARACTER`) one alike — so it costs no characters and `read_runs` skipped it as an empty portion: nothing reported that a selection held a picture at all. Pictures now travel on the runs (`images`), `list_images` reports them by document, section, paragraph, range or selection with the address of the anchor and the text it is anchored to, and `export_image` writes one out through `com.sun.star.graphic.GraphicProvider.storeGraphic` (`inline=true` also returns it as an MCP image block, which `ai_interface` builds from `_image_content`).
- Replacing text **destroys an inline picture**: measured, the rewrite of the stretch that *begins* at the anchor offset kills it, while a stretch that *ends* there leaves it, and one starting a character later leaves it too. So a picture travels on the run that starts at its offset, `_plan_run_rewrite` keeps that run when its text is unchanged, and `replace_runs` refuses otherwise — a picture cannot be handed back through a tool call the way a comment can, since a `Graphic` does not fit in JSON. `_flattening_loss` counts them and `replace_range` names them in its refusal (`images_dropped` when `flatten=true`). An `AT_CHARACTER` picture survives a rewrite, its anchor moving to the start of the replaced stretch, so it is no reason to refuse one.
- **Selecting a picture leaves no text selection.** `controller.getSelection()` then hands back the picture *itself* — an `SwXTextGraphicObject` supporting `com.sun.star.text.TextGraphicObject`, with `getName()` and no `getCount` — where selecting text hands back an `SwXTextRanges` collection. Every selection-based tool therefore failed with "the selection is not a text range: getCount", and `get_cursor_info` with "no text selection" from `unotxvw.cxx`, which left a caller unable to say which of two pictures was in front of it. `_selected_graphics` reads it (a multi-shape selection comes as a collection to filter): `list_images({"selection": true})` reports the selected picture with `scope: {"selection": "picture"}`, `export_image` with no name writes it (`was_selected`), `get_cursor_info` answers `selection_kind: "picture"` with the picture described, and the text tools refuse by *naming* what is actually selected.
- A picture's own name (`Name`) is how a caller points at one; `Title` and `Description` are the title and the alternative text; `Width`/`Height` are the frame in 1/100 mm, while `Graphic.SizePixel` is the picture's own resolution and `Graphic.MimeType` its type (`image/x-vclgraphic` means "whatever LibreOffice holds in memory", not a file type). `GraphicURL` throws on read — do not reach for it. A picture *can* be put back from its `Graphic` with its size, title and alternative text, which is how a restore would work if one is ever wanted.
- A style's **own definition** is readable through `getPropertyState`: `DIRECT_VALUE` for a property the style sets, `DEFAULT_VALUE` for one it inherits. For "Text body" that is 8 properties of 195, and they match its `<style:style>` element in `styles.xml` exactly — so `describe_style` answers "what is this style" from the running document, and nobody needs to unzip the file to find out. It reports `set_here` (the definition, values in mm/pt/percent with the raw number kept), `effective` (a curated set of what is in force, each saying `this style` or `inherited`), the parent chain, `FollowStyle`, `isUserDefined()`/`isInUse()` — which are **methods**, not properties, unlike `IsAutoUpdate` and `Hidden` — and every property with its state under `all_properties`. `DisplayName` is the *UI* name ("Body Text"), which is not the `style:display-name` in the file ("Text body").
- Three measured facts shape the document-level tools. `storeAsURL` with **no `FilterName` writes ODF whatever the file is called**: a document "saved as .docx" came out as ODF with a `.docx` name (`mimetype: application/vnd.oasis.opendocument.text`), which is worse than a refusal, so `save_document` picks the filter from the extension (`WRITER_SAVE_FILTERS`), refuses an extension it does not know, and sends `pdf` to `export_document` — `storeAsURL` with a PDF filter would leave the document claiming to *be* a PDF. `storeAsURL` is Save As, not a copy: the document goes on living at the new URL, where `storeToURL` (which `export_document` uses) leaves it where it was.
- `doc.close(True)` closes a **modified** document without a murmur and the changes are gone — no dialog, no veto. So `close_document` refuses a document with unsaved changes unless `unsaved` says `"save"` or `"discard"`, refuses `"save"` for a document that has never been saved, and leaves the document open if the save fails rather than closing it anyway.
- **UNO has no rename.** `storeAsURL` under a new name leaves the old file exactly where it was — both files afterwards — and LibreOffice writes a fresh `.~lock.<name>#` beside the new one. `rename_document` therefore keeps the old file unless `delete_original=true`, in which case it also removes the stale lock of the old name, and it says in the result which happened. A bare name keeps the document's directory; a name with no extension keeps its format. `os.unlink` is the standard library, not an external program, so this stays within the constraint above.
- **A table cell is its own text.** A caret in one belongs to the cell's `XText`, not to `doc.getText()`, so `paragraph_index` is `None` there and every address-based tool answers "outside the body text" — correctly, since addresses count body paragraphs and skip tables. Where the caret is needs no searching: the view cursor carries the table in `TextTable` and the cell in `Cell`, and the cell names itself (`CellName` = "A1"). `get_cursor_info` reports that as `in_table`, `list_tables` lists the tables (with `after_paragraph`, the count of body paragraphs before each, since that is the only honest way to place one), and `read_table` reads a grid or one cell.
- Cell text is read with `getString()` on the cell, not with `table.getDataArray()`: the data array turns a number into a float and flattens a cell of several paragraphs into one line, where `getString()` keeps the line breaks. A cell merged away is absent from `getCellNames()` and comes back as `null` in the grid.
- Formatting a table, all measured: the grid is the **`TableBorder2`** struct (`TopLine`, `BottomLine`, `LeftLine`, `RightLine`, `HorizontalLine`, `VerticalLine`) and the `Is*Valid` flag beside each line **must be set or the change is dropped**; `Distance` in the same struct is the padding in every cell. A cell's background is `BackColor` with `BackTransparent` turned **off** — a cell has no `FillStyle` and no `FillColor` at all, which is the exact opposite of a paragraph, where `ParaBackColor` is unwritable and `FillStyle` is the way in. Column widths are the separator positions against `TableColumnRelativeSum` and come back rounded (3000 reads as 2999), so they are never compared for equality. A cell is an `XText`: its paragraphs take `ParaStyleName` and a cursor over it takes character formatting. `format_table` does all of that in one undo step, and `cells` accepts a list, `"A1:B2"`, `"row:2"` or `"column:B"`.
- Everything the look of a table is made of is **readable** through UNO, and `describe_table` reports it in the units `format_table` takes: the `TableBorder2` lines as width in mm and `#RRGGBB`, `Distance` as the padding, `BackColor` (meaningful only with `BackTransparent` off) for the table and every cell, the cells' paragraph styles, and with `runs=true` the coloured pieces of their text. Without it, the only way to learn a table's borders and backgrounds was to unzip the document and read `styles.xml` — which an assistant did, twice. A fresh table already carries a thin grid of its own (0.18 mm, black), so "no border was asked for" is not the same as "no border".
- Making a table is three UNO calls — `doc.createInstance("com.sun.star.text.TextTable")`, `initialize(rows, columns)`, `text.insertTextContent(range, table, False)` — and **where** it is inserted decides whether the text survives it: at a paragraph's **start** the table lands between paragraphs and the text is untouched; at its **end** the paragraph is split and an empty one is left behind; with `absorb=True` over a paragraph the text goes but an empty paragraph stays. So `create_table` always inserts before the paragraph its address names. A name set on the table before insertion is kept. Clearing the paragraphs a table stands in for takes two steps, since `setString("")` over them collapses them into one empty paragraph which `removeTextContent` then takes away; `text.removeTextContent(paragraph)` removes a whole paragraph, and `removeTextContent(table)` a whole table, leaving the text around it alone.
- **A selection running from text through a table comes back as one range over the body text**, with the cells' text folded into its string by newlines — in a real document, 318 characters where the paragraph held 206 — so nothing about the string says a table is in there, and `_locate_range` hands back a body address whose length runs past its paragraph. `setString` over such a range **destroys the table**: measured, one table in, none out, the document collapsed into a single paragraph. The flatten guard could not see it, being scoped to one paragraph. `_range_spans` now walks the body and compares regions (`compareRegionStarts`) to say which paragraphs and which tables a range covers: `get_cursor_info`'s selection reports `contains_table`, `tables` and `paragraphs`, `list_tables` reports `in_selection`, `read_runs` reports `spans_tables` and says its runs are only the paragraph's, and `replace_range`/`replace_selection` refuse such a range by name and size unless `flatten=true`, which then reports `tables_dropped`.
- **A table's `Width` is not in 1/100 mm.** A default table spanning a 170.01 mm text area reports 115596, and a real document's table reported the same number, so translating it invented a table 1.16 metres wide. What is measurable is each column's share: `TableColumnSeparators` are positions against `TableColumnRelativeSum` (10000) — three equal columns came back as 3333 and 6666 — which is what `column_widths_percent` reports.
- An annotation refuses the object `getSelection()` hands back — and a cursor made *from* it — with "no SwTextAttr inserted?" from `unofield.cxx`, while the same stretch is accepted when the cursor is walked from its start to its end. Measured after the address matrix showed `add_comment` failing on a selection and nothing else did; `_anchor_comment` now rebuilds every anchor that way, so "comment on what I selected" works.
- Which address forms each tool takes was measured rather than assumed, and the schemas now say it: everything takes a paragraph, a block, a range and the selection; a **table cell** is taken by all of them except `format_paragraph` (paragraph fills need a body paragraph), the scoping tools `list_comments`, `list_images` and `check_spelling`, and `create_table` (which puts a table between paragraphs, not inside a cell).
- An address covered **one** paragraph — `offset` and `length` count characters within it — so "replace these fifteen paragraphs with a table" could not be said at all, and an assistant went to raw UNO to set a selection instead, writing in its notes that the server had no way to do it. It was right. `{"paragraph": N, "through": M}` now covers whole paragraphs from the first to the last, and `select` sets the document's selection to any address, so what a tool is about to work on can be shown to the human too.
- Text is addressed five ways: `{"paragraph": i, "offset": k, "length": n}` (body paragraphs, tables skipped), `{"paragraph": i, "through": j}` for a block of whole paragraphs, `{"table": "Table1", "cell": "A1", "offset": k, "length": n}` for a table cell — offsets count the cell's own text, where the break between its paragraphs counts as one character, and the table may be left out when the caret is in one — `{"selection": true}`, or `{"anchor": "a7f3c1"}`. An address may carry an anchor **beside** its numbers — that is how the reading tools hand one out — and then the anchor decides and the numbers are only what was true when it was read; a *paragraph* anchor takes an `offset` and a `length` counted within it, a text anchor refuses them since it already covers exactly its stretch, and only `selection` is refused beside an anchor. Refusing `table`/`cell` there made every `find_text` hit inside a table cell unusable as an address — caught by the live harness, never by the fakes, which do not search cells.
- **A bookmark is the document's own handle on a place**, where an anchor is the session's. Measured: a bookmark over a range and one at a caret are both `com.sun.star.text.Bookmark` contents whose anchors address cleanly; their markers disturb no offsets, unlike a comment's; `setName` renames one in place and `removeTextContent` takes it away leaving the text; and a **rewrite does not destroy a bookmark** — replacing the very words it covered left it in the document, where the same rewrite takes a comment or a field with it. A name that is already taken is **not** refused by Writer: it silently mints "name Copy 1", so `add_bookmark` refuses it instead. Placing them costs what placing comments cost — 21 bookmarks addressed one at a time were 6.4s on a real document, 0.69s through the one sweep of `_addresses_in_order`.
- **A caption's number is a field that counts itself, and a cross-reference is a field that follows it.** Measured, all of it. A caption is the category, a `com.sun.star.text.TextField.SetExpression` attached to a **sequence master** (`com.sun.star.text.FieldMaster.SetExpression.<Category>` — a fresh document carries Illustration, Table, Text, Drawing and Figure, the element names come back spelling `fieldmaster` in lower case while `getByName` takes the capital spelling, and a category nobody has is made by creating a master with `SubType = SEQUENCE`), then the separator and the text. `SequenceValue` is an **identity, not a number**: captions made 1, 2, 3 with a fourth put in front of them read 2, 0, 1, 3 while showing 2, 3, 4, 1 — so a reference binds to a caption by that value and the number it shows follows the document, which is the whole point of the thing. `getTextFields()` hands the captions out in the order they were *made*, so `_captions` sorts them by address, and a caption's own line comes from the paragraph its address names, since a range's `getText()` is the whole body.
- Where a caption paragraph can go was measured too: a paragraph break at the **end** of a paragraph leaves an empty paragraph directly after it — *before* a table that follows, not after — and one at the **start** leaves an empty paragraph directly before it, after any table in between. So a caption below a table is a break at the start of the paragraph after it, one above a table is a break at the end of the paragraph before it, and a table that **opens the document** has nowhere above it, which is refused rather than quietly written below. A break also leaves the cursor in the *new* paragraph in one case and the old one in the other, so `insert_caption` writes through a fresh cursor into the paragraph it worked out.
- **A reference to a heading is a reference to a bookmark**, and the name matters. Writer's own dialog leaves a mark named `__RefHeading__…`; a bookmark *given* that name **becomes** one — measured: it vanishes from `getBookmarks()`, so nothing can ever find it again, and a second one on the same heading throws `IllegalArgumentException` from `unobkm.cxx`. `insert_cross_reference({"heading": N})` therefore leaves an ordinary bookmark named after the heading, which the Navigator shows and `list_bookmarks` reports, and reuses a bookmark already covering the whole heading so that ten references leave one bookmark. `ReferenceFieldSource` is 0 reference mark / 1 sequence / 2 bookmark / 3 footnote / 4 endnote and `ReferenceFieldPart` 0 page … 5 category and number, 6 only caption, 7 only sequence number; `ONLY_CAPTION` eats a ": " separator and leaves a " – " one ("– A dashed caption"). A heading's *number* needs chapter numbering and shows nothing without it.
- A reference whose target is gone shows **"Error: Reference source not found" in the text of the document**, in the office's language, and nothing else says which reference it was. So `insert_cross_reference` checks the target before writing anything, and `list_references` says `broken` per reference by checking the targets itself rather than reading that sentence.
- **An index's entries are body paragraphs, so writing one moves every address below it.** Measured: a table of contents inserted into a six-paragraph document cost one paragraph going in and four after its first `update()` — a title and three entries — and on a real 303-paragraph document 8 paragraphs for 7 entries. So `insert_index` and `update_indexes` report `paragraphs_added` / `paragraphs_moved`, and a plan that mixes indexes with addressed edits writes the indexes last. The entries wear "Contents Heading" and "Contents 1…10", `IsProtected` is True, and a heading rewritten shows in the old words until the index is updated — which is the whole reason the tool exists.
- `CreateFromOutline` defaults to **False** on a fresh `ContentIndex` and `CreateFromMarks` to True, so an index inserted with UNO's own defaults lists **nothing**; `insert_index` turns the outline on, since a table of contents built from the headings is what the words mean. An index names itself ("Table of Contents1", "Alphabetical Index1") and `doc.getDocumentIndexes()` hands them out under those names, which is how one is named for updating or removing. `UserIndex` is created under that name and answers with `UserDefinedIndex` — the two do not match. Removing one takes its paragraphs with it (`anchor.getText().removeTextContent(index)`), and an index mark is `com.sun.star.text.DocumentIndexMark` with a `PrimaryKey`, inserted with absorb **True**, which keeps the text it marks.
- **A footnote's mark is a character of the paragraph, so it is the same shape as a field and the opposite of a comment.** Measured: a footnote after "query" leaves `A query1 is the entry point` — the superscript number is one character of the string, the portion is of type `Footnote` carrying the note in `Footnote`, and it costs one position for cursor movement. `_position_in` skipped it the way it skips a comment's marker, so every address after a mark was one character to the right, which left a stray letter behind when the text around a mark was rewritten; it counts a `Footnote` portion now exactly as it counts a `TextField` one. A rewrite **destroys the note silently** — one footnote in, none out, the number left as ordinary text — so `read_runs` reports `note` on the run that is one, `_flattening_loss` counts them beside the fields, `replace_range` refuses (`notes_dropped` under `flatten`) and `replace_runs` refuses to rewrite the run a mark sits in while happily rewriting the runs around it.
- An **endnote supports `com.sun.star.text.Footnote` as well as `com.sun.star.text.Endnote`**, so the two are told apart by asking for Endnote, never for Footnote. `doc.getFootnotes()` / `doc.getEndnotes()` are *indexed*, not named, and a note carries no id of its own (`ReferenceId` was 0 for the first), so `update_note` and `delete_note` name one by where its mark sits — the same rule, and the same refusal when an address covers two, as `delete_field`. `Label` is empty while Writer numbers the note itself and can be set to a mark of one's own; the note's text is an `XText` (`note.getText().setString(...)`); and a footnote inside a **table cell** works, its mark addressing as a cell address.
- **A protected section is not protected against this server — or any other.** Measured: with `IsProtected = True` on a section, `replace_range` wrote through it and so did a bare `setString`; UNO raises nothing and reports nothing, because protection stops the reader's *keyboard* and that is all it was ever for. So the refusal is ours: `_protected_section_over` compares the range against every protected section (two UNO calls, and none at all in a document with no sections) and `replace_range`, `replace_selection` and `replace_runs` refuse with `READ_ONLY` naming the section, unless `allow_protected=true` says the caller means it. Without that, a translation pass rewrites the one part of a document its owner locked.
- A **section does not touch the paragraph numbering**: six body paragraphs before one was made over two of them, six after, and six while it was hidden — `IsVisible = False` leaves its paragraphs in the enumeration and readable, so hidden text is still addressed and still read. Sections nest (`ParentSection` / `ChildSections`), `Name` is a plain property that renames one in place, `TextColumns.getColumnCount()` is **0** until columns are set (so one column reports as one), and removing a section leaves every paragraph it held. `list_sections` scopes by **overlap** rather than by where a section starts, since "which sections is this paragraph in?" is the question a caller has.
- **A header belongs to a page style, not to the text**, which is why a running title in the old language survives a translation of the body — nothing in the body is what the reader sees up there. Measured: `HeaderIsOn` must be true before anything else answers (while it is false, `HeaderIsShared`, `FirstIsShared` and `HeaderHeight` all read **None**); **switching a header off destroys its text** — off and on again left both sides empty, so `remove_header_footer` is destructive and hands back what it took; `HeaderIsShared` true makes `HeaderText` and `HeaderTextLeft` the same text, and with it false `HeaderText` follows the **right** page; `FirstIsShared = False` is what gives a first page its own. A header's text is an ordinary `XText` (paragraph style "Header"), so a page number is a `TextField.PageNumber` inserted into it — `set_header`/`set_footer` turn `{page}`, `{pages}`, `{title}`, `{date}`, `{author}` and `{file}` into those fields, and "Страница {page} из {pages}" came back as "Страница 16 из 16" on a real document. `doc.getTextFields()` does report fields living in a header, and their anchors are outside the body, so they have no paragraph address. `isInUse()` on a page style answered False for every style in a headless document that plainly used one, so it is reported and never relied upon.
- **`IsLandscape` turns nothing.** Measured: setting it true left the page 21001 × 29700 — upright, with only the flag moved — so `set_page_layout` swaps `Size` itself to match the word it was given. Page measurements **round** through twips: A4 answers a width of 21001 and a margin written as 1500 reads back as 1499, so millimetres are reported to two decimals and never compared for equality (`_paper_named` allows 5/100 mm either way). `TextColumns.getColumnCount()` on a page style is **0** both before columns are set and after being set to one.
- A page break is `BreakType` on the paragraph that follows it — a pyuno enum whose `.value` reads "PAGE_BEFORE" — with `PageDescName` beside it to switch page style at that point, which is how a document turns landscape half way through. **Clearing `PageDescName` with `None` throws** (`CannotConvertException: Type 0 is not supported`, `convert.cxx:444`); `""` clears it and reads back as None, and `PageNumberOffset` refuses None the same way. `from com.sun.star.style import BreakType` fails with "No module named 'com'" — the *constant* has to be imported (`from com.sun.star.style.BreakType import PAGE_BEFORE`), which is what `__import__(..., [name])` does in `uno_layout`. Line numbering is document-level `LineNumberingProperties`, whose `Separator` **throws on read** while everything beside it answers.
- `describe_style(family="page")` was answering with the paragraph's questions — character weights and paragraph margins — on a thing that has none. `STYLE_EFFECTIVE_PAGE` is what is in force on a page instead (size, orientation, margins, columns, numbering, the header and footer switches), `Size` renders as "210.01 × 297.0 mm" rather than a struct dump, and `TextColumns` as a number.
- **Clearing `HyperLinkURL` does not take a link's look away.** Measured on a real document of 34 links: the navy underline is the character styles `UnvisitedCharStyleName` ("Internet link") and `VisitedCharStyleName` ("Visited Internet Link"), and after the URL alone was cleared the run's `CharStyleName` read "Internet link" and the text stayed blue. `remove_hyperlink` clears all five properties, so the words come back as ordinary text — and `format_range` can now *make* a link, which it could not: it had every character property except that one, so turning a word into a link meant rewriting the text with `replace_runs`. A link split by a bold word inside it is several portions and **one** link, which is how `list_hyperlinks` reports it.
- A link into the same document (`#Name`, optionally `#Name|outline`) is checked against the bookmarks, sections, reference marks, frames, tables, pictures and heading texts, and reported `broken` when nothing matches. An http link's `broken` is left **null**: nothing in this server may reach the network, so it is neither claimed sound nor claimed broken. Listing them all walks every portion of the document — 1.2s on 300 paragraphs — so a scoped call narrows the walk to the paragraphs its scope covers (0.012s for one paragraph, 0.5s for a section), and `_comment_scope` now honours `{"paragraph": N, "through": M}` as the block of paragraphs it means everywhere else, which every scoping tool gets.
- **There is no move and no copy on the model**, and that is why moving a paragraph used to mean reading it, deleting it and writing it again — losing its comments and its pictures on the way. Measured: `.uno:MoveDown` / `.uno:MoveUp` through `DispatchHelper` move whatever the **view cursor** covers and carry everything with it (a comment stayed on its words, a bold run stayed bold, and the move reversed exactly); and the controller's own transferable — `getTransferable()` on the selection, `insertTransferable()` where it should land — copies a block with its comments and never touches the system clipboard. Both work on the reader's selection, so `move_paragraph` and `copy_paragraphs` put it back afterwards, as the review tools do.
- Splitting is a paragraph break at an offset, and a comment spanning the cut **survives across both halves** (its anchor read "Пер\nвый" afterwards). Joining is deleting the single newline between two paragraphs — a cursor at the end of the first, `goRight(1, True)`, `setString("")` — and `merge_paragraphs` checks that the character it is about to delete really is `"\n"`, so a table standing between two paragraphs is left alone rather than destroyed.
- **A tool must not report a scope wider than the answer it gives.** `read_runs` over `{"paragraph": N, "through": M}` answered with the *first* paragraph's runs while reporting `spans_paragraphs: [N … M]`, which reads as a promise to have returned them all; a caller checking the formatting of a section paid a call per paragraph before spotting the pattern. It now reads every paragraph in the block in one walk (`paragraphs`, `paragraphs_read`, capped at `MAX_RUN_PARAGRAPHS` = 50 with `truncated`), each run carrying its own paragraph in its address. The cost is the runs' own property reads — about twelve bridge calls apiece — so a block of fifteen paragraphs is ~2s over a socket; what it saves is fifteen round trips, not the reading. `_runs_in` takes the paragraph object from a caller that already holds it, since finding one by index walks the body.
- Beside that, `replace_runs` over a block was **silently destructive**: measured, three paragraphs in, one out, the breaks gone and `success: true`, because the runs are one paragraph's and `setString` over the whole block takes the paragraph breaks with it. It refuses a multi-paragraph address now with `WOULD_LOSE_FORMATTING` and the paragraphs named, unless `flatten=true` asks for the join knowingly.
- **Automatic is not black.** `CharColor` and `CharBackColor` both read **-1** on text nobody has coloured, and writing -1 back is the only way to take a colour off — a caller stripping someone else's highlighting had to write `#000000`, which looks the same and means something else. `_colour` accepts `"auto"`/`"automatic"` (and -1) for that, `_colour_name(-1)` is `"automatic"`, and the round trip name → int survives. Where a fill is not a colour the same word means the absence: a **paragraph** goes to `FillStyle = NONE` rather than a fill of colour -1, a **table cell** goes back to `BackTransparent = True`, and a **border** has no automatic colour at all and says so.
- **A paragraph style can be searched for; a character style cannot.** Measured: `SearchStyles = True` with the style's name as `SearchString` makes `findAll` answer with every paragraph in that style — 0.003s where comparing `ParaStyleName` means walking the body — and the same search finds **nothing** for a character style, which is walked for portion by portion. `find_by_style` places only the hits it will report, since placing 184 of them costs 1.7s.
- **Direct formatting is `getPropertyState` on the range**, the same DIRECT_VALUE / DEFAULT_VALUE a style answers, with `AMBIGUOUS_VALUE` for a range whose parts differ (and no value at all to read off it). `getPropertyStates` answers for a whole list in one call. Three measured facts shape the clean-up: **character formatting applied to a *whole* paragraph lands on the paragraph** — a paragraph made bold end to end answers DEFAULT_VALUE for `CharWeight` on its range while the value reads 150 — so both the range and the paragraph are asked and both are cleared, or "clear this paragraph" does nothing; a **hyperlink survives** `setAllPropertiesToDefault` and so does a **character style**, so a clean-up keeps inline code and links; and `CharStyleName`/`CharLocale` are left alone unless named outright, since taking a run's language off would hand it back to the style's.
- **Writing styles**: `insertByName` puts a new one in its family, `setName` renames it **and the text wearing it follows**, and `removeByName` lets the text **fall back to the parent** — a paragraph in a removed style read "Preformatted Text". Removing a **built-in** style is accepted by UNO and does nothing at all, no exception and no removal, so `delete_style` refuses one rather than reporting it done. Properties are checked before anything is written: a bad name used to be found after `insertByName`, so a refused call left the style behind.
- Replacing one style with another was 20.5s for 184 paragraphs, because each place was found and then **addressed**, and each address walked the body. One walk sets them all — a paragraph carries `ParaStyleName` itself and a portion is a range carrying `CharStyleName` — 0.25s for the same 184. The walk must include the **table cells**: the body held 162 of those paragraphs and Writer's search found 184, the other 22 being inside cells, so "throughout" means the cells too (a scoped replacement leaves them alone, since a scope names body paragraphs).
- **The undo history is the document's, not the server's.** Measured on `doc.UndoManager`: the titles say whose each step is — this server's edits read "MCP: replace text", the reader's typing `Typing: “…”` and `New Paragraph`, and an API edit made without an undo context of its own `Insert $1`. So `undo` stops at the first step it did not make and names it, refusing with `INVALID_PARAMETER` unless `include_others=true`; an assistant cleaning up after itself must not take back what the human typed. The methods are `getAllUndoActionTitles` / `getAllRedoActionTitles` (not "…Strings"), and `undo()`/`redo()` do not appear in `dir()` on the proxy yet work; undoing fills the redo list and a new edit empties it. A step made through the dispatcher inside `_guarded_edit` — converting a table to text, say — is one entry like any other, and undoing it put the table back on a real document.
- **`convertToTable`'s shape was read by introspection** (`com.sun.star.beans.Introspection` → `getMethods` → `getParameterInfos`), after a guess at `PropertyValue` wrappers failed with "value is not interface": `TableRanges` is `[][][]XTextRange` — rows, cells, and the two ranges that start and end each cell — followed by `[][]PropertyValues` for cells, `[]PropertyValues` for rows and `[]PropertyValue` for the table. With that shape, **nothing between the first cell's start and the last cell's end is dropped**: ranges over the pieces of "Имя\tВозраст" put the tab at the head of the next cell, ranges ending after their separator put it at the tail of their own, and only taking the separators out first gives clean cells — measured all three ways. Rows of different widths are refused rather than guessed at. The way back is Writer's own `.uno:ConvertTableToText` with the caret in the table, and its `Delimiter` must be a **string**: the tab's number did nothing, silently.
- **The reader and the agent can edit one document at the same time, and three of four ways of doing it go wrong.** Measured on a copy of a real document in a GUI LibreOffice, with real keystrokes from `xdotool` (which go through the same event loop as a human's) while the agent edited over MCP. Every UNO call takes the SolarMutex the keyboard takes too, so the two interleave call by call, never tool by tool. What that does, in four scenarios:
  - **addressing by paragraph number fails even inside one call.** A `batch_live` of ten `replace_range` steps on `{"paragraph": N}` while the reader pressed Enter above wrote **none** of its ten intended paragraphs and overwrote others instead ("Enum types…", "Validate that…"); when a line arrived *between* two steps, the next step hit the paragraph the previous one had just written, so the agent overwrote its own work — ten writes, six paragraphs changed. Reading the document a fraction of a second before the call did not help, since the typing lands between the steps of that call;
  - **anchors hold.** The same batch addressed by `anchor` wrote **10 of 10** intended paragraphs and nothing else, the paragraph numbers the steps reported climbing as the reader inserted lines mid-batch (163, 166, 169, 173…);
  - **the view-cursor tools lose data.** While the reader typed, `move_paragraph` selected a far paragraph through the view cursor, a keystroke arrived while it was selected, and a line of code (`"""`) elsewhere in the document was **replaced by the letters "fg"**, which were missing from the reader's own line. Neither side is told. The same holds in principle for everything that works through the view cursor — `copy_paragraphs`, `accept_tracked_changes`, `reject_tracked_changes`, `convert_table_to_text` — measured for `move_paragraph` only;
  - **undoing a batch takes the reader's typing with it.** Six of ten lines typed while a batch's undo context was open were folded **into** the "MCP: batch of 10 steps" entry — they are not separate `Typing:` entries — and `undo_live` on that entry erased them with the agent's edits (four of ten lines left). The ownership guard cannot see it: the entry's title says it is ours.
  The rig had two artefacts of its own, neither of LibreOffice: `xdotool`'s first keystroke of a run sometimes came out in the active keyboard layout ("H" as "Р") or went missing, and `read_paragraphs` answers at most 200 paragraphs a call, so a snapshot has to page. The author a recorded change is given when the agent edits was not part of this.
- **Addressing by anchor is now the default, not an option.** `find_text`, `read_paragraphs` and `read_runs` hand every address out with the anchor that holds it (`anchors: false` turns it off), so a caller that passes an address straight back is anchored without knowing it; `_resolve_address` prefers the anchor whenever one is there. Two kinds of anchor: a **text** anchor is a held cursor over a stretch, and a **paragraph** anchor — what `read_paragraphs`/`read_runs` hand out — is the `SwXParagraph` object *plus* a cursor at its start, because a paragraph object alone is not enough. Measured on the object: it follows insertions above it, survives a rewrite of its own text and a `replace_runs` through it (where a cursor over the same stretch collapses), throws `SwXParagraph: disposed or invalid` when its paragraph is merged into the one before or removed — which is how `paragraph_now` refuses by name instead of writing somewhere else — and on a **split it stays with the text after the cut**, so a break at the end of a paragraph leaves the object naming the new empty one, which is why the start cursor decides the position and the object only decides whether the paragraph is still there. Holding them is cheap (300 held cursors did not slow an edit: 0.47s against 0.50s) but making them is not, since each address is a walk — `anchor` for 300 paragraphs took 26s, so `pin_paragraph_numbers` places them in one sweep. Handing them out costs what it costs: 200 paragraphs read 0.37s → 0.92s, 50 search hits 0.448s → 0.605s.
- **A paragraph has no number in UNO, so a tool must not pay for one nobody asked for.** Measured: `_locate_paragraph` counts the paragraphs before a place at **0.55 ms each** over a socket — 0.01s at paragraph 5, 0.49s at 1000, 1.08s at 2000, 2.95s at 4072, 3.95s at 6900 — and `get_cursor_info` paid it on every call, plus `getString()` on every paragraph it passed (437 KB of text pulled over and thrown away) purely to total up `document_offset`. So the walk is now opt-in: `number` counts the index, `character_offset` counts the characters too, and what comes back by default is `address`, an **anchor** on the caret's paragraph, for two UNO calls. Measured on the same document: **8s → 0.025s** for the default call, 5.3s with `number: true`. `_locate_paragraph` takes `count_characters` and `_locate_range` a `find_paragraph` flag for the same reason — every caller that never read `chars_before` was paying for it. The number's cost does not disappear, it moves: a tool addressed by that anchor still walks to work out which paragraph to *report*, 12.0s then 6.6s and 5.6s for `read_runs` through the same anchor, which is the next thing to take out.
- **Two measured facts let a paragraph be worked on without its number at all.** A **text cursor is an `XEnumerationAccess`**: it hands out the paragraphs it covers, and a collapsed caret yields the one it stands in — so `_paragraph_from(range)` has the paragraph object for two UNO calls where reaching it by index is a walk. And a **portion of type `Frame` hands out what is anchored there** through `createContentEnumeration`, so a paragraph names its own pictures; `_runs_in` used to ask `_images_in` instead, which asks *every picture in the document* whether it belongs here — four UNO calls apiece, hundreds of pictures in a real guide, on every call that reads runs. Both were probed on a live Writer before anything was built on them.
- **So `read_runs` through an anchor never works the number out.** An address that is nothing but `{"anchor": …}` resolves through the anchor's own paragraph, reads its runs, and addresses each of them `{"anchor": …, "offset": k, "length": n}` — which resolves back the same way, `_within_paragraph` counting inside the paragraph the anchor names. `paragraph` comes back `null`, deliberately: nobody counted it. The walks that had to go were four, and the last one hid in `_note_what_is_out_of_reach` → `_range_spans`, which counted the paragraph to fill in a field the answer does not even show for a single paragraph. Measured end to end on the 6981-paragraph guide, caret at paragraph 4072: "where am I" **8s → 0.013s**, "read the runs there" **8–12s → 0.008s**. Reading the same paragraph *by number* is 0.77–1.7s, and a block of ten 4.2–5.8s against 7.6–23s, both from the picture scan going.
- **A file nobody has opened is invisible to this server**, and until now it could make a document and close one but not *open* one — so a caller with a path in hand had nothing to say, and `scripts/read_tools_check.py` could not stand up its own document. `open_document` loads one and, when that file is already open, answers with the document it finds (`already_open`) instead of opening it twice, which is what makes it safe to call before any piece of work. `hidden` and `read_only` are the two load properties worth having.
- **Numbering a list is a sweep of the body, and anchoring it is not.** Measured on the 519-page guide: `list_bookmarks` cost **20.1s** for 195 bookmarks and `list_images` **142s** to say which pictures stand in *one* paragraph — the first because `_locate_matches` walks every paragraph of the document to place anything at all, the second because describing a picture places it and there are 566 of them. Both now hand out an anchor apiece and cost **0.36s** and **1.5s**; every picture in the document comes back in 2.6s where numbering them all takes 123s (`number: true`, kept for showing a human where things are). Scoping without numbers is `_scope_over`, which compares the scope's range with each item's — four UNO calls apiece and no walk. Two things follow: the fast listing is in the order the document names its things, not reading order, so the answer says which (`order`), and a caller that needs reading order asks for numbers (`insert_cross_reference` and `list_reference_targets` do). `scripts/read_tools_check.py` calls every reading tool against that guide and reports which of them still hand out addresses without an anchor.
- **Every listing now places its things by anchors, and counts numbers only when asked.** The sweep that numbers them is one walk of the body however many things there are, so it cost the same whether a document held one section or a hundred; measured on the 519-page guide, before and after: bookmarks 20.1s → 0.36s, pictures in one paragraph 142s → 1.5s, cross-references 11.7s → 4.9s (and every picture in the document, which used to be unthinkable, 2.6s), fields 14.1s → 5.7s, sections 4.2s → 1.05s, reference targets 79s → 7.0s. Three things had to give way with them: `_captions(place=False)` skips the sweep when only the categories and sequence ids are wanted, which `_known_targets` is; `_headings_as_targets(bookmarks=False)` skips the *second* sweep that says which bookmark already covers a heading; and `list_anchors` places its anchors only with `number`, since saying whether one is alive and what it holds costs nothing while saying where it points is that walk. A heading's own address stays a number, because a reference to a heading is made *by* that number. `delete_field` now compares an address by **what it resolves to** rather than by how it was written, or an anchor could never name the field it holds.
- **An answer names a place once, and the anchor in it says which kind it is.** `{"anchor": {"anchorId": "84b81c", "type": "paragraph" | "text"}}`, inside the `address` and nowhere else — the first cut of this had the id in the `address` *and* the typed object beside it, and the reader's verdict on reading two records of one anchor was "выглядит как усложнение". It was: an agent then has to know which of the two to pass back. The kinds differ where it matters — only a `paragraph` anchor counts an `offset` and a `length` within itself, a `text` anchor covers exactly its stretch and refuses them — so the type belongs where the id is. `_anchor_token` accepts either the object or a bare id, so everything written against the old form still resolves, and `_anchor_handle` is the one place the shape is made. `read_runs` no longer lists the paragraph anchors beside the runs that already carry them, and `list_anchors` reports the type on the anchor rather than as a `kind` of its own.
- **A range says what it covers, so the selection needs no numbers either.** Measured: a *cursor* is an `XEnumerationAccess` and one spanning three paragraphs with a table between them enumerated `['Two', <table>, 'Three', 'Four']` — the paragraphs **and** the table, from the range alone. So `get_cursor_info` answers about the selection from `_contents_in(span)`: `paragraphs_selected`, `tables`, `contains_table`, and an **anchor over the selection** in `address`; the numbers come only with `number: true`, since each is a walk of the body. `read_runs` given that anchor reads **every** paragraph the selection covers — `_runs_over` holds an anchor per paragraph and addresses its runs by it — where before it read the first and said the range went further. Two things had to be got right: the enumeration must be made on a **cursor**, since the range `getSelection()` hands out answered with one paragraph for a selection that plainly ran through a table; and a table is not a paragraph, so `paragraphs_selected` counts only what has `getStart`. Measured on the 6981-paragraph guide with nine paragraphs selected: `get_cursor_info` **18.7s → 0.025s**, and reading all nine through its anchor 0.135s, with no paragraph number worked out anywhere.
- **The reader that pages through a document takes an address back.** `read_paragraphs` handed out an `address` with an anchor on every paragraph and then accepted only a number as its `start`, so the one thing a caller does with a long document — read a window, then the next — forced it back to numbers between calls, and the habit the guide asks for broke at the first page. `start` is now a number *or* an address (anchor, paragraph, or a block, whose `through` also says how many to read when `count` does not), and the `start` in the result says which number it came to. Checked live: with a paragraph inserted above, the handed-out address still reads its own paragraph while the number it was handed out with reads another.
- **None of the reading windows is a ceiling any more.** `read_paragraphs` clamped `count` at `MAX_PARAGRAPH_COUNT` = 200 and `list_anchors` at 200; both are defaults now, and a caller who asks for everything gets it — the whole of a 6981-paragraph document in one call, 4.8s and 1.57 MB of JSON. One real bound is left and it is the anchors: a read of more paragraphs than `MAX_ANCHORS` = 2000 with `anchors` on would hand back tokens the store let go **while the answer was being built**, so it is refused with `INVALID_PARAMETER` naming both ways round, rather than quietly answered with dead tokens or with anchors silently turned off. The result now says `anchors` — what actually happened — beside the paragraphs. `MAX_ANCHORS` moved to `uno_values` with the other bounds, since `uno_reading` needs it too and the parts do not import each other.
- `get_outline` has the same `start` and a `count`, and gives every heading an anchored address of its own. 200 is what a window nobody asked about holds (`DEFAULT_OUTLINE_ENTRIES`) and **not a ceiling**: `count` may ask for the whole map, and the 938 headings of that guide come back in one call — 2.0–4.0s without anchors and 3.7–4.2s with, 93 KB of JSON, the spread between runs wider than the cost of the anchors themselves, so the earlier "12 ms an anchor" was noise. It used to stop at 200 and say `truncated`, with **no way to reach the rest**: on a 519-page guide with more than 200 headings, the chapter an assistant was asked about was simply not in the map, and the only way to it was a text search. It now reports `headings_before`, `total_headings` and `more` beside the window; `truncated` is kept, meaning what it always meant — there are headings this answer does not carry. Its `doc` moved to the end of the signature, where every other bridge method keeps it.
- **Handing anchors out by default made the one tool that inspects them unusable.** `list_anchors` placed every anchor by reaching its paragraph by number — `_paragraph_at`, a walk of the body — and then walked again to read that paragraph's text, so a session that had read a few hundred paragraphs paid thousands of walks: on a 6981-paragraph document the call did not answer in **fifteen minutes**, and since the server takes its calls one at a time, nothing else answered either. `_body_sweep` now walks the body once for the whole call, `_paragraph_holding` finds an anchor's paragraph by **halving that list** — thirteen region comparisons against seven thousand element fetches, which is what keeps a listing cheap *after* an edit has moved every remembered index — and a text anchor's address is located with its paragraph handed over as a hint. The listing is paged at `MAX_ANCHOR_REPORTS` = 200, `held` counting them all and `more` saying there are further ones, because reporting a thousand anchors is a payload nobody reads. Measured on that document with 1000 anchors held: 2.4s for a page of 200, 3.4s for the last page.
- **A batch pins the paragraph numbers its steps name before the first step runs**, and translates each step's numbers as it goes (`_numbers_in` / `_as_numbered_now` in `mcp_batch_tools.py`, `paragraphs_moved` per step, `paragraphs_pinned` / `paragraphs_not_pinned` in the outcome). Without that, a step that adds a paragraph — a caption, an index — sent every step after it one paragraph astray *inside a single call*, which is the same failure the reader's typing causes and needs the same cure. A step whose pinned paragraph has been merged away is refused with `INVALID_ADDRESS` and not run.
- **An index is not a place, and a held cursor is.** Every address above counts paragraphs, so an insertion or a deletion above one changes its number, and a plan made from a single search went stale as it was carried out — which is why the note for a real document said to work through it backwards. UNO keeps a text cursor up to date instead, and `anchor` hands out a token for one. Measured, in this order: text inserted or a whole paragraph removed **above** a held cursor leaves the text it covers untouched; text inserted **inside** it is taken in, so a cursor over a paragraph still covers that paragraph; the cursor that performs `setString` **keeps the new text**, while any *other* cursor over the same stretch **collapses to an empty position** without throwing; a cursor whose paragraph is removed goes the same way, empty but still usable (`compareRegionStarts` still answers); and a cursor into a cell whose table is removed, or into a document that is closed, **throws** "SwXTextCursor: disposed or invalid". An empty cursor is indistinguishable from a caret by asking — `isCollapsed` says true for both — so `uno_anchors` records what each anchor covered when it was made and refuses a stale one by name instead of resolving it to the hole it left.
- Because `_resolve_address` hands back the anchor's **own** cursor, a replacement made through an anchor leaves it pointing at the replacement — that is the measured `setString` rule above, and it is deliberate. It holds only while nothing moves a resolved range: no tool does today (the one `gotoRange` in `create_table` walks a cursor of its own), and one that did would silently move the anchor with it.
- Anchors are per open document, kept by `RuntimeUID` — the document's own id while it is open ('1', '2', …), the only thing that tells two untitled documents apart. They live as long as the server process and are capped at `MAX_ANCHORS` (the oldest let go), because they are a way through one piece of work, not a mark in the file. A **bookmark** is the other half of that trade: it is saved in the document, survives reopening, and shows up in the Navigator — measured to move with the text the same way.
- A cell filled with `setString("a\nb")` holds **one paragraph with line breaks in it**, not two paragraphs — so its runs are the runs of that one paragraph, and colouring a piece of code inside a cell splits them as anywhere else. (A cell filled by typing Enter does hold several; both are handled.) The runs of a cell come back addressed **to that cell** (`{"table", "cell", "offset", "length"}`): a body address with `paragraph: None` resolves to nothing, which is what made `replace_runs` in a cell fail with "paragraph must be a non-negative integer". `_address_in` is the single place that decides which kind of address a piece gets.
- Finding which cell owns a range: **the range's own text *is* the cell**, an `SwXCell` supporting `com.sun.star.text.CellProperties` that names itself in `CellName`, so the cell needs no searching. Only its table does, and the one test that works is `compareRegionStarts`: 0 for the cell itself, and it **throws** for a cell of another table. `createTextCursorByRange` is no test at all — it accepted a range from a different cell of a *different table*, which is how a hit in B2 was once reported as A1. Measured, after the live harness caught it. `_locate_range` produces an address from a range, `_resolve_address` turns one back into a range, and every tool goes through them — see `docs/superpowers/specs/2026-08-18-writer-text-tools-design.md`.
- `tests/live/writer_tools_check.py` checks the bridge against a real headless LibreOffice. Run it with `/usr/bin/python3` (the venv has no `uno`) whenever bridge code changes; a green pytest run alone does not mean the UNO calls work.
- **A paragraph break reads as `"\r\n"` on Windows, not `"\n"`.** A cursor that selects one break with `goRight(1, True)` answers `'\r\n'` there (measured on Writer for Windows), so `merge_paragraphs` — which checked for `"\n"` before deleting — joined nothing while reporting `success` with `joins: 0`. Compare against both. `tests/fakes_text.py` takes `break_string` for the same reason.
- **A batch given a `document` must hand it to its steps.** The paragraphs a batch pins and the undo group it opens belong to that document, but a step that named none acted on the *active* one — another document when the reader had switched windows, so every step failed with `no body paragraph N` or, worse, wrote into the wrong file. `batch_live` now adds `document` to each step whose tool takes one and that did not name its own. Found by running the batch on a scratch document while a different one was in front; the fakes had only ever held one document.
- **Paths and `file://` URLs are not `"file://" + path` on Windows.** The URL is `file:///C:/Users/x` and the path `C:\Users\x`; `uno_values._file_url` and `_document_path` go through `Path.as_uri()` and `url2pathname`, and so do the fakes in `tests/`. Joined by hand the URL came out `file://C%3A%5C…` and every save, page render and picture export failed.
- Two ways the formula tools paid for what they report, both fixed with tests that fail without the fix. `read_runs` called `_formula_places`, which addresses **every** formula anchor and so walks the whole body, to answer about one paragraph — the habit the bullet above exists to forbid; `_formulas_in` compares each object's anchor with the paragraph first, exactly as `_images_in` does for a picture, and then measures it with `_locate_range` against the paragraph it is already known to be in, which does no walk at all (checked live: the sweep is never entered). And `_formula_places` collected an anchor and its text in one `try`, so a formula that answered once and was gone by the next read left the lists of different lengths and **every formula after it took another's place** — measured in the fakes with a model that answers once, which is what a formula deleted mid-call looks like from here.
- **A formula is an embedded object, and no paragraph-reading tool sees it.** It is a `com.sun.star.text.TextEmbeddedObject` (Math, class id `078B7ABA-54FC-457F-8551-6147e776a997`) whose text is `obj.Model.Formula` in StarMath. An inline one adds **no character** to the paragraph and is anchored at an empty range, so `read_paragraphs` shows "равен  от всего объема" for "равен 1/5 от всего объема" and `list_formulas` gives the place plus `text_before`/`text_after`. So `read_paragraphs` adds `formulas` and `text_with_formulas` (`⟦formula: …⟧` at the offset) to a paragraph that holds one, and `read_runs` a `formulas` list — beside `text`, never in it, because every offset counts in the plain string; StarMath uses both braces and brackets, hence the unusual mark. `getEmbeddedObjects()` answers in no order (Object3, Object2, Object1) and holds charts too — formulas are picked out by having `Model.Formula` and sorted by position. A duplicate name is **refused** with an error (no "Copy 1" as with bookmarks). See `uno_formulas.py`.
- **A new formula object does not size itself.** It stays 35.3 × 4.7 mm whatever is written in it, so every formula came out squashed or stretched — the reader saw them "badly distorted". `getEmbeddedObject().getVisualAreaSize(1)` says what the Math document takes, in the unit `getMapUnit(1)` names (9 = twips for a formula; 1 twip = 1.764 hundredths of a mm), and `_fit_to_formula` copies that into `Width`/`Height`. Not verified by eye: `render_page` (PNG) and PDF export draw **blank gaps** for embedded formulas in this setup — including for a document that came with real ones — so the picture cannot show either the distortion or the fix; look at it in the LibreOffice window.
- **Changing `Model.Formula` is not an undo step of the text document.** It writes into the formula's own document, so an undo context around it stays empty and makes no entry; `set_formula` reports `was` so it can be put back. Adding one *is* a step (`MCP: add a formula`).

## Conventions

- Structured returns: the external server uses Pydantic models (`DocumentInfo`, `TextContent`, `ConversionResult`, `SpreadsheetData`) so MCP clients get schemas; the plugin returns plain dicts because Pydantic isn't available there.
- Root `mcp-helper.sh` and `generate-config.sh` are one-line `exec` wrappers around `scripts/`.
- `docs/` is extensive and largely aspirational — verify claims against code before relying on them.
